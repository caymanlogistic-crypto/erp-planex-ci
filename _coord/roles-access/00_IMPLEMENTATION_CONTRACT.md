# ERP PLANEX — ГИБКАЯ СИСТЕМА РОЛЕЙ, ДОСТУПОВ И ЗАКРЕПЛЕНИЙ

## ФИНАЛЬНОЕ ТЕХНИЧЕСКОЕ ЗАДАНИЕ / IMPLEMENTATION CONTRACT

---

# 1. Цель

Необходимо заменить существующую преимущественно hard-coded систему бизнес-ролей ERP PLANEX на гибкую управляемую систему.

Существующие роли:

- Руководитель;
- Логист+;
- Логист

после внедрения становятся начальными предустановленными ролями новой системы.

Руководитель должен иметь возможность без изменения программного кода создавать новые роли, например:

- Диспетчер;
- Бухгалтер;
- Менеджер;
- Старший логист;
- любые другие роли компании.

Система должна оставаться простой, визуально понятной и соответствовать существующей архитектуре ERP PLANEX.

Не создавать универсальную сложную ACL-платформу.

---

# 2. Общая модель

Основная модель:

**Учётная запись → Членство в компании → Одна роль → Доступ к страницам → Доступ к регулируемым данным → Персональные исключения → Закрепления**

Разделяются следующие понятия:

### Роль

Базовые настройки пользователя внутри конкретной компании.

### Доступ к страницам

Какие конкретные страницы ERP пользователь может открыть.

### Доступ к данным

Для ограниченного набора сущностей:

- Все;
- Только свои;
- Нет доступа.

### Персональные настройки

Исключения из настроек роли для конкретного пользователя.

### Закрепления

Определяют, какие конкретные:

- Клиенты;
- Перевозчики;
- ТС;
- Водители

относятся к пользователю в режиме `Только свои`.

---

# 3. Multi-company

Одна глобальная учётная запись может состоять в нескольких компаниях.

Модель:

**одна учётная запись → несколько company memberships.**

Для каждого сочетания:

`user + company`

отдельно хранятся:

- роль;
- статус;
- персональные настройки страниц;
- персональные настройки данных;
- закрепления.

Пример:

Компания А:

`Иванов → Логист`

Компания Б:

`Иванов → Руководитель`

Права одной компании не влияют на другую.

При переключении компании ERP использует настройки membership именно выбранной компании.

---

# 4. Глобальная учётная запись и данные компании

Не дублировать пользователя как отдельную независимую учётную запись для каждой компании.

К глобальной учётной записи относятся существующие в ERP authentication/profile данные, в частности:

- логин;
- пароль / password hash;
- ФИО;
- иные существующие глобальные данные авторизации пользователя.

К membership компании относятся:

- `company_id`;
- `role_id`;
- активен / отключён;
- персональные настройки страниц;
- персональные настройки data-scope;
- закрепления.

Смена роли в одной компании не меняет роль пользователя в другой компании.

---

# 5. Добавление нового пользователя

Во вкладке **Пользователи** должна быть возможность:

**+ Добавить пользователя**

Добавление должно поддерживать оба сценария:

1. создаётся совершенно новая глобальная учётная запись;
2. существующая глобальная учётная запись добавляется ещё в одну компанию.

Не создавать две глобальные учётные записи одного человека только потому, что он работает в нескольких компаниях.

---

# 6. Если учётной записи ещё нет

Если указанный глобальный пользователь ещё не существует:

1. создаётся глобальная учётная запись через существующий canonical механизм ERP;
2. создаётся membership текущей компании;
3. Руководитель назначает роль;
4. membership создаётся активным либо в штатном статусе, предусмотренном текущей ERP.

Не создавать отдельный механизм авторизации специально для новой системы ролей.

Использовать существующий механизм ERP для:

- логина;
- пароля;
- восстановления доступа;
- authentication.

---

# 7. Если учётная запись уже существует

Если глобальная учётная запись уже существует, например пользователь работает в другой компании:

- новую глобальную учётную запись создавать нельзя;
- создаётся только новое membership текущей компании;
- существующие глобальные логин, пароль и ФИО не копируются в новую company-specific запись;
- существующие memberships других компаний не изменяются.

Руководитель текущей компании получает возможность назначить только данные нового membership:

- роль;
- статус;
- персональные настройки;
- закрепления.

Нельзя показывать Руководителю права, роли или внутренние данные memberships этого пользователя в других компаниях.

---

# 8. Повторное добавление

Если пользователь уже состоит в текущей компании, повторное membership не создаётся.

Система сообщает, что пользователь уже добавлен в компанию, и позволяет перейти к его существующей настройке.

Уникальность membership:

`user_id + company_id`

---

# 9. Изменение глобальных данных

Роль и права компании не должны изменять глобальную authentication identity пользователя.

В частности изменение:

- роли;
- персональных прав;
- закреплений;
- статуса membership

не должно создавать новый логин или новый пароль.

---

# 10. Предустановленные роли

После миграции должны существовать:

- Руководитель;
- Логист+;
- Логист.

Их начальные настройки должны воспроизводить **фактический существующий доступ** пользователей до миграции.

Нельзя ориентироваться только на текстовое название старой роли.

---

# 11. Одна роль в компании

Пользователь имеет только одну базовую роль внутри конкретной компании.

Не вводить:

- несколько ролей одновременно;
- объединение ролей;
- inheritance пользовательских ролей;
- приоритет нескольких ролей.

Индивидуальные отличия реализуются персональными настройками.

---

# 12. role_id

Каждая роль получает стабильный внутренний:

`role_id`

Отображаемое название роли не является её технической идентичностью.

Переименование обычной роли не должно менять:

- права;
- пользователей;
- закрепления;
- серверную авторизацию.

---

# 13. Создание обычной роли

Руководитель может создавать произвольные роли.

Новая роль создаётся fail-closed:

### Страницы

Все закрыты.

### Регулируемые данные

Все:

`Нет доступа`

После этого Руководитель самостоятельно включает необходимые настройки.

---

# 14. Названия ролей

Название обычной роли должно быть уникально внутри компании.

Не допускать очевидных дублей из-за:

- регистра;
- лишних пробелов.

Зарезервированы системные названия:

- Руководитель;
- superadmin.

Обычную роль с таким названием создать нельзя.

---

# 15. Копирование обычной роли

При копировании роли копируются только:

- настройки страниц;
- режимы доступа к данным.

Не копируются:

- пользователи;
- memberships;
- персональные настройки пользователей;
- закрепления.

После копирования роли полностью независимы.

---

# 16. Удаление роли

Обычную роль можно удалить только если она не используется ни одним membership компании.

Учитываются:

- активные пользователи;
- отключённые пользователи.

Если роль используется — удаление запрещается.

Например:

> Роль используется 4 сотрудниками. Сначала назначьте им другую роль.

Не выполнять автоматическое переназначение пользователей внутри операции удаления роли.

---

# 17. Защищённый Руководитель

`Руководитель` является специальной системной ролью компании.

Её системность определяется стабильным внутренним ключом/признаком, а не только текстом названия.

Руководитель всегда имеет внутри своей компании:

- все страницы;
- все данные;
- управление ролями;
- управление пользователями;
- управление персональными настройками;
- управление закреплениями.

Для Руководителя нельзя:

- удалить системную роль;
- переименовать её;
- закрыть страницу;
- установить `Только свои`;
- установить `Нет доступа`;
- добавить персональный запрет страницы;
- добавить персональное ограничение данных.

**Руководителя нельзя ограничить персональными исключениями.**

---

# 18. Несколько Руководителей

В компании может быть несколько активных Руководителей.

Это штатный сценарий.

---

# 19. Последний активный Руководитель

В компании всегда должен оставаться минимум один активный Руководитель.

Если пользователь является последним активным Руководителем, сервер обязан запретить:

- отключение;
- смену роли;
- удаление membership;
- исключение из компании;
- любую другую операцию, оставляющую компанию без активного Руководителя.

Проверка обязательна на backend.

Блокировки кнопки в UI недостаточно.

---

# 20. Копирование Руководителя

Роль Руководителя можно использовать как шаблон.

При копировании:

- копируется текущий набор страниц;
- копируются текущие режимы данных;
- создаётся обычная роль.

Системный статус Руководителя не копируется.

Если позже появляется новая ERP-страница:

- Руководитель получает её автоматически;
- роль, когда-то скопированная с Руководителя, автоматически её не получает.

---

# 21. superadmin

Существующий `superadmin` сохраняется отдельным техническим механизмом.

`superadmin`:

- не является company role;
- не участвует в конструкторе ролей;
- не создаётся и не редактируется Руководителем;
- не является membership-ролью компании;
- не показывается в списках сотрудников для закреплений;
- не участвует в закреплениях;
- сохраняет существующий технический системный доступ ERP.

Не объединять `superadmin` и компанию-роль Руководитель.

---

# 22. Основная единица доступа — страница

Основной permission новой системы:

**конкретная ERP-страница.**

Не вводить универсальные permissions:

- View;
- Create;
- Edit;
- Delete;
- Export;
- отдельные кнопки;
- отдельные поля;
- отдельные popup.

Если пользователь имеет страницу, он получает её штатный функционал с учётом data-scope.

---

# 23. page_key

Каждая защищаемая конечная страница должна иметь стабильный:

`page_key`

Он не зависит от:

- названия;
- URL;
- положения в меню;
- родительского раздела;
- порядка.

Переименование или перемещение страницы не сбрасывает права.

---

# 24. Единый реестр страниц

Должен существовать один canonical registry защищаемых страниц.

Не создавать второй вручную синхронизируемый список для админки.

Из реестра определяются:

- `page_key`;
- название;
- раздел;
- группа;
- порядок;
- связанные защищённые server actions/endpoints.

Из этого же реестра строится матрица административного доступа.

---

# 25. Новая страница

Новая зарегистрированная страница автоматически появляется в настройке ролей.

По умолчанию:

### Руководитель

Разрешено автоматически.

### Обычные роли

Запрещено.

Новая страница не должна автоматически расширять права существующих пользователей.

---

# 26. Дерево страниц

Матрица доступа визуально повторяет актуальное меню ERP PLANEX.

Разделы и группы используются только для визуальной структуры.

Права задаются конечным страницам.

Групповой checkbox может:

- включить все дочерние страницы;
- выключить все;
- показывать intermediate state.

Отдельного серверного permission группы не создаётся.

---

# 27. Пользовательское меню

Меню строится из эффективных page permissions.

Если конечная страница недоступна — скрыта.

Группа показывается, если доступна минимум одна дочерняя страница.

Раздел показывается, если существует минимум одна доступная вложенная страница.

Меню не является механизмом безопасности.

---

# 28. Direct URL

Если `page_key` запрещён, пользователь не должен получить страницу через прямой URL.

Защита выполняется сервером до выдачи защищаемых данных.

---

# 29. Server actions

К page access должны быть привязаны:

- GET;
- POST;
- AJAX;
- JSON endpoints;
- create/update/delete actions;
- modal loaders;
- загрузки;
- server actions страницы.

Скрытая кнопка не является защитой.

---

# 30. Endpoint нескольких страниц

Если один backend endpoint legitimately используется несколькими страницами, для него явно регистрируется набор разрешающих `page_key`.

Для выполнения конкретной операции достаточно, чтобы пользователь имел доступ **хотя бы к одному зарегистрированному `page_key`, которому сервером разрешено выполнять именно эту операцию**.

Логика:

`authorized_page_key_1 OR authorized_page_key_2 OR ...`

При этом:

- endpoint сам знает допустимый набор `page_key`;
- клиент не может произвольно передать любой `page_key` и таким образом получить доступ;
- разрешение страницы не отменяет data-scope;
- data-scope проверяется независимо после page-level проверки;
- доступ через одну страницу не должен давать возможность выполнить другой режим операции, который этой странице не принадлежит.

---

# 31. Fail-closed endpoints

Если защищённый endpoint должен участвовать в access system, но его `page_key` или разрешающий набор страниц не определён:

**доступ запрещается.**

Не использовать fail-open.

---

# 32. Права без перелогина

Изменения прав должны действовать без logout/login.

Нельзя считать сохранённую при входе роль и permission-set вечными до окончания сессии.

Следующий защищённый запрос после изменения настроек должен использовать актуальное effective access.

После refresh меню перестраивается.

---

# 33. Персональные страницы

Для обычного пользователя каждая страница имеет:

- По роли;
- Разрешить;
- Запретить.

`По роли` означает использование роли.

`Разрешить` персонально открывает страницу.

`Запретить` персонально закрывает.

Для этого нельзя использовать обычный двухсостояниевый checkbox.

---

# 34. Визуализация персональной страницы

При `По роли` показывать фактическое значение, например:

`По роли · доступно`

или:

`По роли · закрыто`

Персональное отличие обозначать:

**Персонально**

---

# 35. Регулируемые данные

Data-scope вводится только для:

- Клиентов;
- Перевозчиков;
- ТС;
- Водителей;
- Линейных рейсов;
- Рейсов отходов.

Не применять такую модель автоматически ко всем данным ERP.

---

# 36. Заявки ФЭО

Заявки ФЭО остаются page-only.

Для них не вводить:

- Все;
- Только свои;
- ownership;
- ручные закрепления.

Если страница ФЭО доступна — пользователь видит штатное содержимое страницы компании.

---

# 37. Режимы роли

Для регулируемой сущности обычная роль имеет:

- Все;
- Только свои;
- Нет доступа.

---

# 38. Персональные режимы данных

У конкретного обычного пользователя:

- По роли;
- Все;
- Только свои;
- Нет доступа.

Персональное значение заменяет роль только для этого пользователя.

При `По роли` показывать фактическое значение, например:

`По роли · Только свои`

---

# 39. Нет доступа

`Нет доступа` означает отсутствие нормальной возможности работать с сущностью.

Запрещаются:

- списки;
- карточки;
- создание;
- изменение;
- удаление;
- поиск;
- autocomplete;
- выбор объекта;
- API;
- direct URL;
- экспорт;
- счётчики;
- альтернативные выдачи защищаемых данных.

---

# 40. Страница есть, данных нет

Возможна конфигурация:

`Страница Клиенты → разрешена`

`Клиенты → Нет доступа`

Тогда сама страница открывается, но клиентские данные сервером не выдаются.

Показывается стандартное состояние:

> Нет доступа к данным этого типа.

Создавать клиента пользователь также не может.

---

# 41. Только свои — справочные объекты

Для:

- Клиентов;
- Перевозчиков;
- ТС;
- Водителей

`Только свои` означает:

**объекты, закреплённые за пользователем в данный момент.**

Создатель не является бессрочным владельцем.

---

# 42. Many-to-many

Закрепления обязательно many-to-many.

Один объект может одновременно быть закреплён за несколькими сотрудниками.

Например:

ООО «Транс»:

☑ Иванов
☑ Петров
☐ Сидоров

При `Только свои` ООО «Транс» доступно Иванову и Петрову.

---

# 43. Автозакрепление нового объекта

При успешном создании нового:

- Клиента;
- Перевозчика;
- ТС;
- Водителя

объект автоматически закрепляется за **конкретным пользователем компании, который выполнил создание**.

Это правило применяется к любому company user, включая Руководителя.

То есть если объект создаёт Руководитель, закрепление за Руководителем также создаётся.

Хотя Руководителю закрепление не требуется для текущего доступа, оно сохраняется как нормальная business assignment и будет иметь значение, например, если его company role впоследствии будет изменена после появления другого Руководителя.

---

# 44. superadmin и system/import

`superadmin` не участвует в обычных закреплениях.

Если объект создаётся:

- background job;
- import;
- migration;
- system process;
- integration

и отсутствует достоверный конкретный company user, совершивший создание:

**автоматическое закрепление не создаётся.**

Нельзя искусственно назначать такой объект:

- Руководителю;
- первому Логисту;
- superadmin;
- случайному сотруднику.

Если импорт действительно выполняется от имени конкретного авторизованного company user и существующая бизнес-операция достоверно считает его создателем, допускается обычное автозакрепление за этим пользователем.

---

# 45. Кто меняет закрепления

Изменять закрепления может только Руководитель.

Обычный пользователь не может:

- назначить другого сотрудника;
- снять себя;
- передать объект;
- обойти это ограничение через endpoint.

Руководитель может назначить объект одному или нескольким пользователям и снимать любое закрепление.

---

# 46. Создатель ≠ текущий владелец

Создатель может сохраняться как историческое/служебное поле.

Но текущий доступ определяется закреплениями.

Пример:

1. Иванов создал объект.
2. Он автоматически закреплён за Ивановым.
3. Руководитель добавил Петрова.
4. Видят оба.
5. Руководитель снял Иванова.
6. При `Только свои` объект остаётся только у Петрова.

---

# 47. Независимость уровней

Закрепления независимы для:

- Клиентов;
- Перевозчиков;
- ТС;
- Водителей.

Доступ к Перевозчику не означает автоматический доступ ко всем его ТС.

Доступ к ТС не означает автоматический доступ ко всем объектам Перевозчика.

---

# 48. Создание связанных объектов

Если перевозчик доступен Иванову и Петрову, а Иванов создаёт его новое ТС:

ТС автоматически закрепляется только за Ивановым.

Петров не получает его автоматически.

Аналогично для Водителя.

---

# 49. Минимальный связанный контекст

Если пользователю доступно ТС, но недоступен сам Перевозчик, можно показать минимальный необходимый контекст:

`Перевозчик: ООО «Транс»`

Но это не выдаёт права:

- открыть карточку Перевозчика;
- искать его;
- получить каталог;
- получить остальные его ТС;
- получить остальных Водителей.

---

# 50. Никакого автоматического распространения прав

Не создавать цепочку:

`ТС → Перевозчик → все ТС → все Водители → все рейсы`

или наоборот.

Руководитель самостоятельно определяет необходимые закрепления.

---

# 51. Линейные рейсы

Режимы:

- Все;
- Только свои;
- Нет доступа.

`Только свои` = Линейные рейсы, **созданные самим пользователем**.

Ручных закреплений рейсов нет.

---

# 52. Рейсы отходов

Аналогично:

- Все;
- Только свои;
- Нет доступа.

`Только свои` = рейсы, созданные пользователем.

Ручных закреплений нет.

---

# 53. Рейсы не участвуют в переназначениях

Линейные рейсы и Рейсы отходов:

- отсутствуют во вкладке `Закрепления`;
- не имеют manager checkbox;
- не переназначаются этой системой.

---

# 54. Canonical mapping сущностей

В пользовательском интерфейсе используются названия:

- Клиенты;
- Перевозчики;
- ТС;
- Водители.

Реализация обязана использовать существующие canonical ERP entities, а не создавать параллельные сущности.

---

# 55. Клиенты

Пользовательское понятие:

**Клиенты**

должно использовать существующую canonical Client-модель ERP и существующее семейство `company_clients*`.

---

# 56. Перевозчики

Пользовательское понятие:

**Перевозчики**

в этой системе относится к существующей canonical сущности `Contractor` / `company_contractors*`.

Существующая отдельная сущность:

**Исполнители рейса / RouteExecutor**

автоматически с Contractor не объединяется.

В первой версии она регулируется page-level доступом.

---

# 57. ТС — обязательная technical фиксация перед реализацией

Пользовательское понятие:

**ТС**

означает отдельную canonical сущность транспортного средства существующей ERP.

Однако до написания миграции, schema changes и access logic разработчик обязан точно зафиксировать фактический current technical mapping данной сущности.

Необходимо определить и документировать:

- canonical DB table;
- primary identifier;
- canonical model/service;
- существующий `entity_type`;
- существующие routes/actions;
- связи с закреплениями/другими объектами.

В текущем коде могут использоваться технические идентификаторы типа:

`vehicle_unit`

даже если пользовательская сущность называется `Vehicle / ТС`.

Реализация обязана использовать фактическое существующее canonical значение.

Нельзя без проверки создать новый:

- `entity_type=vehicle`;
- новую таблицу Vehicle;
- новый параллельный идентификатор;
- второй механизм определения ТС

только ради access system.

---

# 58. VehicleSet и другие транспортные структуры

Режим `ТС` относится именно к canonical единице отдельного транспортного средства.

Он не должен автоматически создавать отдельный data-scope для:

- VehicleSet;
- состава ТС;
- legacy driver-vehicle blocks;
- других агрегированных транспортных сущностей.

Если позднее понадобится отдельное право на VehicleSet — это отдельное ТЗ.

---

# 59. Водители

Использовать существующую canonical Driver-сущность и текущую структуру ERP.

Не создавать новый параллельный каталог водителей ради access system.

---

# 60. Финансы

Старое hard-coded правило вида:

`финансы = только Руководитель`

не должно продолжать блокировать обычную роль после появления новой системы.

Если Руководитель разрешил роли, например:

`Бухгалтер → Закрывающие документы`

пользователь должен получить штатный функционал этой страницы внутри своей компании.

Не создавать отдельный universal finance data-scope.

---

# 61. Сохранение закреплений при смене режима

Переключение:

`Только свои → Все`

не удаляет закрепления.

При возврате:

`Все → Только свои`

старые закрепления снова действуют.

---

# 62. Нет доступа не удаляет закрепления

Переключение:

`Только свои → Нет доступа → Только свои`

не должно потерять предыдущие закрепления.

---

# 63. Закрытие страницы

Если страницу закрыли, data-scope и закрепления не удаляются.

После повторного открытия страницы сохранённая конфигурация продолжает работать.

---

# 64. Смена роли

При:

`Логист → Диспетчер`

сохраняются:

- персональные настройки страниц;
- персональные настройки данных;
- закрепления.

Новая роль становится новой базой.

Персональные исключения продолжают иметь приоритет.

---

# 65. Блокировка пользователя

При отключении membership сохраняются:

- роль;
- персональные настройки;
- закрепления;
- созданные объекты.

Пользователь немедленно теряет ERP-доступ в этой компании.

После повторного включения настройки продолжают действовать.

---

# 66. Отключённый пользователь и закрепления

Если отключённый пользователь имеет закрепления, Руководитель продолжает видеть его в административных списках с отметкой:

**Отключён**

и может перераспределить объекты.

---

# 67. Effective access resolver

Для каждого защищённого запроса применяется единая последовательность.

1. Определить глобального пользователя.
2. Определить активную компанию.
3. Определить membership.
4. Проверить status membership.
5. Обработать технический `superadmin` отдельным существующим механизмом.
6. Проверить системного Руководителя.
7. Для обычного пользователя получить актуальный `role_id`.
8. Рассчитать page permission роли.
9. Применить персональное page exception.
10. Проверить endpoint → page_key mapping.
11. Если используется регулируемая сущность — определить data-scope роли.
12. Применить персональный data-scope.
13. При `Нет доступа` отказать в непосредственном доступе к сущности.
14. При `Только свои`:

- Client / Contractor / Vehicle / Driver → проверить assignment;
- Linear Trip / Waste Trip → проверить creator.

15. При неизвестном защищённом состоянии → deny.

# 95. Обязательный technical discovery перед изменением схемы

До первого изменения DB/schema/access mappings разработчик обязан проверить существующий код и зафиксировать точные canonical technical identities регулируемых сущностей.

Особенно обязательно проверить **ТС**.

Результат должен однозначно определить:

- фактическую таблицу;
- primary key;
- model/service;
- `entity_type`;
- relations;
- routes/actions;
- места существующих ownership/association checks.

Если существующий canonical `entity_type` называется, например, `vehicle_unit`, именно он используется.

Не создавать параллельное имя только потому, что в ТЗ пользовательский термин — `ТС`.

- новой странице;
- неизвестном `page_key`;
- неизвестном endpoint;
- отсутствующей role configuration;
- неизвестном data-scope;
- ошибке определения membership/company.

Защищённый Руководитель является системным исключением и всегда имеет полный доступ внутри своей компании.

---

# 97. Обязательные acceptance scenarios

Необходимо покрыть тестами минимум следующие сценарии.

### Новая роль

Создать Диспетчера → первоначально нет страниц и данных → настроить → назначить пользователю → работает без новой разработки.

### Новая страница

Автоматически появляется в registry/matrix → Руководителю доступна → обычным ролям закрыта.

### Rename / regroup

Переименование и перемещение страницы не меняет permissions.

### Direct URL

Закрытая страница через URL не открывается.

### POST/AJAX

Закрытый server action нельзя вызвать вручную.

### Shared endpoint

Endpoint имеет несколько разрешающих `page_key`.

Пользователь имеет одну из разрешающих страниц → операция разрешена только в предусмотренном для этой страницы контексте.

Data-scope всё равно проверяется отдельно.

### Personal allow

Роль не имеет страницы → конкретному пользователю `Разрешить` → получает.

### Personal deny

Роль имеет → конкретному пользователю `Запретить` → теряет.

### Personal data-scope

Роль `ТС → Только свои`, пользователь персонально `ТС → Все` → пользователь видит все.

### Many-to-many

Один Contractor закреплён за Ивановым и Петровым → оба видят.

### Auto assignment обычного пользователя

Иванов создаёт Contractor → assignment Иванову создаётся автоматически.

### Auto assignment Руководителя

Руководитель создаёт Contractor → assignment Руководителю также создаётся.

### System import

Import без конкретного company user создаёт объект → assignment автоматически никому не создаётся.

### Transfer from creator

Иванов создал объект → Руководитель снимает Иванова и оставляет Петрова → Иванов теряет его при `Только свои`.

### Independent Vehicle

Один Contractor у двух менеджеров → разные Vehicle закреплены независимо.

### Linear trips

`Только свои` показывает creator-owned trips.

Manual assignments отсутствуют.

### Waste trips

Аналогично.

### Все → Только свои

Assignments не потеряны.

### Нет доступа → Только свои

Assignments не потеряны.

### Смена роли

Personal overrides и assignments сохраняются.

### Disable/enable

Роль, overrides и assignments сохраняются.

### Last Руководитель

Его нельзя отключить/перевести/исключить.

### Second Руководитель

После появления второго первого можно перевести/отключить.

### Copy Руководителя

Создаётся обычная snapshot-role без системного auto-access к будущим страницам.

### Finance

Явно разрешённая финансовая страница работает у обычной роли.

### Multi-company

Один account имеет разные роли и assignments в разных компаниях.

### Existing account

Пользователь уже существует в другой компании → новая глобальная учётка не создаётся → добавляется только membership.

### Duplicate membership

Повторное добавление в ту же компанию не создаёт дубль.

### Immediate revocation

Закрыли страницу → следующий защищённый запрос уже запрещён без logout/login.

### Migration

BEFORE ↔ AFTER не содержит необъяснённого расширения или сужения доступа.

# 98. Критерии неприёмки

Доработка НЕ принимается, если:

- новые бизнес-роли снова hard-coded;
- Руководитель определяется только названием;
- Руководителю можно урезать права;
- компанию можно оставить без активного Руководителя;
- `superadmin` превращён в company role;
- роль пользователя глобальна вместо company membership;
- один пользователь не может состоять в нескольких компаниях;
- для существующей учётки создаётся duplicate account при добавлении во вторую компанию;
- права одной компании влияют на другую;
- персональная страница имеет только checkbox без состояния `По роли`;
- персональный data-scope не имеет `По роли`;
- новая страница автоматически открывается обычным ролям;
- изменение menu title/location сбрасывает access;
- direct URL обходит access;
- POST/AJAX обходит access;
- shared endpoint разрешает операцию только потому, что клиент передал нужный `page_key`;
- data-scope перестаёт проверяться на shared endpoint;
- незарегистрированный защищённый endpoint fail-open;
- изменение прав требует login/logout;
- `Нет доступа` скрывает только UI, а данные остаются доступны;
- рейсы попали в ручные assignments;
- один объект нельзя закрепить за несколькими сотрудниками;
- новый Client/Contractor/Vehicle/Driver не закрепляется за фактическим user creator;
- объект Руководителя не получает нормальное assignment;
- system/import без creator искусственно назначает объект сотруднику;
- `Все` или `Нет доступа` уничтожают assignments;
- смена роли уничтожает personal overrides;
- блокировка уничтожает настройки;
- Contractor автоматически выдаёт все Vehicle;
- Vehicle автоматически выдаёт весь Contractor;
- создана параллельная Vehicle/ТС сущность;
- фактический canonical `entity_type` Vehicle не проверен до реализации;
- finance по-прежнему скрыто блокируется old role-name check;
- роль удаляется с неявным автоматическим переносом пользователей;
- копирование роли переносит users/overrides/assignments;
- появился новый журнал истории прав;
- появился новый отдельный admin UI-kit;
- используется popup поверх popup;
- role/user settings сохраняются каждым кликом вместо одной кнопки;
- assignments требуют общей кнопки `Сохранить`;
- migration выполнена без BEFORE ↔ AFTER;
- исторические assignments придуманы без достоверных данных.

# 99. Финальный принцип реализации

ERP PLANEX не требуется универсальная permission platform.

Нужна понятная бизнес-модель:

**Пользователь → Компания → Роль → Страницы → Data-scope → Персональные настройки → Закрепления.**

Руководитель должен самостоятельно и визуально понимать:

- какие роли существуют;
- кто в них состоит;
- какие страницы им доступны;
- какие данные им доступны;
- какие настройки у пользователя наследуются;
- какие изменены персонально;
- какие объекты закреплены за сотрудником.

При выборе реализации использовать вариант, который:

- следует существующей архитектуре ERP;
- использует существующие canonical entities;
- использует существующий UI PLANEX;
- не создаёт параллельных механизмов;
- безопасен fail-closed;
- сохраняет current behavior существующих пользователей;
- однозначно проверяется автоматическими тестами.

**Перед production внедрением обязательны:**

**CODE PASS + CI PASS + MIGRATION BEFORE↔AFTER PASS.**
