# Закрывающие документы завершённых рейсов

Страница `/company/trips/closing-documents` доступна через отдельный permission-key `company.documents.trip_closing` и применяет действующий scope рейсов отходов. По одному рейсу можно раскрыть только одну карточку. В ней собираются подписанный договор или заявка, счёт, акт или УПД, путевой лист и произвольные дополнительные файлы. Сводных боксов статуса нет; полоса комплектности и текст недостающих документов расположены в строке рейса.

«Передать на проверку» отправляет письмо с 30-дневной ссылкой на ZIP через рабочий ящик сотрудника. Получатель определяется исполнителем рейса: `planex` → `info@plan-ex.ru`, `mg_logistic` → `shibanov@mg-log.ru`. Результат SMTP `unknown` блокирует повторную отправку и изменение комплекта до проверки исходящих писем; пользователь может подтвердить, что письмо не отправлено, и разрешить повторную попытку. Ссылка содержит случайный 256-битный токен; архив ограничен файлами этого рейса и компании.

Файлы рейса появляются в общем реестре `/company/finance/closing-documents` у проведённых банковских платежей с активным распределением на обязательства этого рейса: входящих от заказчика и исходящих перевозчику. Частичная оплата подходит; другие хозяйственные платежи без связи с рейсом остаются в реестре без файлов рейса. Внутренний перевод и движение сотрудника не создают такой связи. Один и тот же файл рейса хранится один раз, а повторная синхронизация не добавляет повторных связей. При отмене распределения автоматически созданные связи удаляются только у соответствующего платежа. В финансовом списке договор/заявка и акт/УПД учитываются штатными обязательными категориями; счёт, путевой лист и дополнительные файлы видны как приложения.

Синхронизация срабатывает при добавлении или удалении файла рейса и при создании или отмене распределения платежа. Для старых платежей manual-only workflow `waste_trip_closing_finance_backfill_production.yml` запускает `scripts/waste_trip_closing_finance_backfill.php`. Сначала режим `preview` без записи выдаёт количество недостающих связей по компаниям и SHA-256 плана. Режим `apply` требует тот же digest, точный SHA развернутого кода и явное подтверждение; добавляет только отсутствующие связи, сохраняя существующие ручные и автоматические. Для каждого арендатора в постоянном `storage/backfills/trip-closing-finance` остаётся закрытый JSON-манифест с идентификаторами только вновь созданных связей и контрольной суммой. Номер workflow run служит идентификатором операции.

Режим `rollback` с номером исходного запуска удаляет только записанные в его манифесте связи, предварительно проверив их состав и отсутствие пользовательских правок. Он не удаляет вручную добавленные документы. Откат можно повторить: уже отсутствующие записи пропускаются. Если связь была изменена после загрузки, откат этой компании останавливается для ручного разбора без частичного удаления внутри неё. При ошибке применения в одной компании скрипт пытается компенсировать изменения уже обработанных компаний и сообщает об ошибке компенсации отдельно. Все три режима проверяют точный deployed SHA; запись в production бизнес-данные требует отдельного разрешения OWNER.

Миграция `152_waste_trip_closing_documents.sql` создаёт три новые tenant-таблицы без изменений существующих рейсов и документов. Страница до миграции показывает сообщение о неготовой схеме. Production-применение выполняет только manual-only workflow `waste_trip_closing_152_production_migration.yml` после точного deploy SHA, проверки CI и отдельного разрешения OWNER на изменение production-схемы. Кодовый deploy сам по себе миграцию не запускает.

Локальный тест `tests/waste_trip_closing_finance_mysql_test.php` проверяет миграцию, адресатов, частичную и полную оплату заказчика, выплату перевозчику, отсутствие дублей и посторонних платежей, отмену распределения, историческое применение и точный откат.
