# Исправление складского направления рейса

Страница `/company/warehouses/stock` позволяет руководителю исправить старый рейс, у которого ещё нет записей в `warehouse_movements`. Поддержаны приход на склад, вывоз со склада и перемещение между двумя складами. Фильтры страницы работают без отправки формы.

## Источник и доступ

- Предварительная проверка читает старую базу через существующее подключение `LEGACY_FLIGHTS_DB_*`, которое открывает транзакции только на чтение.
- Проведение использует отдельное подключение `FeoLegacyImportSync::forTenant()` с уже настроенной привязкой одной tenant-БД к той же старой базе. Если привязка отсутствует или имя базы отличается от `LEGACY_FLIGHTS_DB_DATABASE`, операция закрыта.
- Для этой операции аккаунту записи нужны `SELECT` на `warehouses`, `feo`, `flights`, `warehouse_movements`, `UPDATE` на `flights` и `INSERT` на `warehouse_movements`. Все четыре таблицы должны быть InnoDB. Настройка и выдача прав не входят в миграцию приложения.
- Кнопка и JSON-endpoints доступны только роли `company_owner`; POST требует стандартный CSRF-токен.

## Проведение

1. Для рейса, направления и складов проверяются существование и активность складов, состав заявок и наличие полной массы в `feo`.
2. Рейс с любыми прежними складскими движениями блокируется. Для исходящего маршрута по каждой заявке показывается отсутствие или недостаток массы на исходном складе. Оператор может подтвердить списание после просмотра предупреждения; остаток при этом может стать отрицательным.
3. Браузер получает отпечаток проверенного состояния. При подтверждении сервер повторяет проверку под блокировками и отклоняет устаревший отпечаток.
4. В одной транзакции меняются `flights.route_type`, `unload_type` и склады, затем создаются все движения из значений `feo`. Если одна запись не проходит, изменение рейса и все движения откатываются.
5. После commit связанный рейс в tenant-БД обновляется из старой базы. Ошибка обновления зеркала показывается как предупреждение, а складской commit не повторяется. Очередная штатная синхронизация может завершить обновление.

Это исправление предназначено для пропущенного направления без складских движений. Переразметка уже проведённых движений требует отдельного сценария сторнирования и сюда не входит. Время операции для завершённого рейса берётся из `actual_end_date`, для остальных — момент исправления. Масса берётся из текущей строки `feo`, как в штатном legacy-проведении.

Локальная проверка: `tests/warehouse_trip_correction_mysql_test.php` в изолированной MySQL-схеме проверяет приход, вывоз, перемещение, дубль, недостаточный остаток, устаревший preview и откат после ошибки второго INSERT. `tests/warehouse_correction_browser_test.mjs` проверяет фильтры и попап на desktop/mobile с синтетическими ответами API.
