# Договоры логистов

Принятая версия интерфейса: Design Lab `logist-contracts-preview-20261101:v003`.
Логист видит свои последние договоры по рейсу и виду договора. Руководитель видит последние версии всех логистов и рассматривает их после создания. PDF доступен сразу. Новая генерация создаёт следующую версию; прежний PDF, его контрольная сумма и результат рассмотрения сохраняются.

Форма открывается только после полной синхронизации рейсов из существующего источника. Назначенный исполнитель берётся из рейса; если он отсутствует, логист выбирает действующего исполнителя для договора. Выбор не изменяет назначение в рейсе. Начало договора берётся из даты рейса, окончание — через семь дней, ставка вводится вручную, режим НДС по умолчанию «Без НДС». Доступ к рейсу и исполнителю проверяется повторно на сервере.

Для вида «Аренда» используется единственный активный шаблон `vehicle_lease_crew`, для «Субаренда» — `carrier_sublease_crew`. Данные подписи и печати получены из образца OWNER и добавляются к актуальному DOCX перед конвертацией в PDF. На production LibreOffice 7.1.8.1 запускается из отдельного каталога `deploy/logist_contracts_pdf_runtime_7_1_8_1` рядом с ERP. Ручной workflow `logist_contracts_pdf_runtime_provision.yml` собирает его из архивов с закреплёнными SHA-256, проверяет конвертацию штатного DOCX в PDF и активирует каталог целиком. Guarded deploy проверяет этот runtime, `proc_open`, PHP `ZipArchive` и `DOMDocument` до замены ERP. Локальный Windows runtime использует установленный LibreOffice. PDF сохраняется с SHA-256 и проверяется при скачивании.

Имя PDF использует общее правило основного генератора: `Рейс <ID> <фамилия водителя>.pdf`, для субаренды перед расширением добавляется ` Субаренда`. Номер версии остаётся в ERP и не меняет имя скачивания. Печать и подпись привязаны к строке подписи ПЛАНЭКС в шаблоне и не увеличивают её высоту. Их физический размер и смещение повторяют блок подписания на второй странице образца `Рейс 351 Харламов (2).pdf`: печать пересекает строку, подпись лежит поверх её правой части. Складские маршруты проходят через общий `prepareFromTrip`: для погрузки со склада учитываются актуальные перемещения и состав заявок, для выгрузки на склад подставляется его адрес; правило действует также для маршрута «склад → склад».

При создании событие `logist.contract.created` отправляется в активную группу MAX «тестовая» через настраиваемый шаблон каталога событий. Ошибка доставки фиксируется в серверном журнале и показывается создателю договора; сохранённый договор остаётся доступным.

Код и производственная миграция — отдельные операции. `164_logist_contracts.sql` создаёт в каждой активной tenant-базе одну таблицу и запись в `schema_migrations`, существующие рейсы и договоры не меняет. После exact-SHA deploy и отдельного разрешения OWNER ручной workflow `logist_contracts_164_production_migration.yml` сверяет SHA, CI, контрольную сумму SQL, состояние до/после и применяет миграцию. До разрешения production DDL не запускать.

Локальные проверки: `tests/logist_contract_integration_test.php`, `tests/logist_contracts_browser_test.mjs`, `tests/waste_trip_synchronization_mysql_test.php`. Браузерный тест проверяет заполнение ширины таблицы, отсутствие изменения фона при наведении, два столбца попапа на компьютере, роли и узкий экран как регрессию без переработки мобильного дизайна.
