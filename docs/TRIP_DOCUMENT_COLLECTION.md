# Запрос и сбор документов на перевозку отходов

Два permission-key: `company.documents.request` и `company.documents.collection`.
Помощник — единственный активный `enshina` внутри текущей компании, без выбора роли по названию и без нового пользователя. Все действия ПЛ проверяют его membership на сервере. Существующие страницы подрядчиков, водителей, ТС и исполнителей сохраняют собственные ACL.

Запрос закрепляет юридическое лицо, рабочую почту ПЛ и ответственного Л. Оба отслеживаемых ящика должны быть настроены и проверены существующим механизмом EmployeeMail. Внутренний пакет направляется Л по рабочей почте выбранного юрлица и пользователям `spugov`, `gluhova`, `ashibanov` по основным email учётных записей. Это уточнение OWNER от 20.09.2026: два адреса используются только логистами и помощниками. Пароли внутренних получателей не требуются. Основной email не подменяет рабочую почту Л/ПЛ.

Состав сверяется с существующими карточками и явно классифицированными документами. Минимум: применимые реквизиты подрядчика, данные водителей и частей ТС, паспорт/ВУ и СТС каждой части. Полный пакет дополнительно требует контакт для документов и фотографии каждой части ТС. Дополнительные телефоны — при наличии. Документы ПР, включая диагностическую карту, не блокируют оба этапа и не создают третьей рассылки. В письме нет строки с наименованием/ИНН перевозчика и нет города в теме.

ПЛ открывает штатные попапы карточек, относит вложения входящего письма к связанным карточкам/типам, проверяет комплектность и предпросмотр. Налогообложение сохраняется в существующую `contractor_tax_history`. Изменение финансовых условий рейса не предоставляется; при смене подрядчика в существующем исполнителе требуется проверка логистом.

Не более двух принятых SMTP-сервером внутренних рассылок: минимум, затем изменённые данные и новые/изменённые файлы до полного. Если всё готово сразу — одно письмо «Полные данные». Предпросмотр имеет срок 20 минут, проверяет изменение адресатов, настроек, карточек и файлов. Файлы копируются в неизменяемый снимок исходящего пакета. Каждая попытка имеет снимок в истории. SMTP после DATA с неопределённым результатом не повторяется автоматически: ПЛ фиксирует подтверждённый результат и основание проверки.

IMAP первоначально фиксирует текущую границу INBOX; старую переписку не импортирует. Читает заголовки ограниченными порциями, тела — только при сильном совпадении Message-ID/References или случайного токена запроса. Одинаковый ответ обоим адресатам сохраняется один раз. Неоднозначное письмо доступно после явной привязки. HTML отображается текстом, файлы проходят существующие проверки и скачиваются как вложения.

Существующая админка MAX (`/company/max/settings`) управляет шестью событиями `documents.*`: новый запрос, ответ, напоминание, ошибка, минимум, полный пакет. Для первых четырёх можно выбрать группу ПЛ отдельно от двух общих событий. OWNER временно выбрал существующую группу «ТЕСТОВЫЙ» для обоих назначений. Настройки не создаются автоматически миграцией; журнал и повтор доставки — существующие MAX.

## Ввод в эксплуатацию

Код deploy и production migration — разные операции. Для migration 140 требуется отдельное разрешение OWNER. Guarded workflow `trip_document_140_production_migration.yml` требует точного deployed canonical SHA и успешного CI, проверяет read-only снимки, создаёт только шесть новых tenant-таблиц и журнал миграции. Существующие рейсы не изменяет.

На SpaceWeb расписание задаётся отдельным заданием в панели хостинга: каждую минуту (`* * * * *`) выполняется `cd /home/s/spugovxsim/planexp/public_html/erpv2 && APP_PUBLIC_URL=https://plan-ex.ru/erpv2 /usr/bin/php8.5 scripts/trip_document_worker.php --company=25 >> logs/trip_documents.log 2>&1`. SSH-команда crontab на этом хостинге недоступна. Другие задания сохраняются. Workflow не изменяет планировщик: после миграции `--check` проверяет схему и согласованность часового пояса PHP/БД, затем gate ждёт нового heartbeat от планировщика (до 90 секунд). Старый heartbeat не считается успехом; ручной запуск worker в gate не подменяет расписание. Worker использует MySQL named lock, сохраняет курсоры, снимает зависшие попытки в неопределённый статус, создаёт сроки и выполняет очередь вне браузера.

До объявления готовности проверить сохранённые профили ПЛ/Л без отправки писем, минимальные grants существующего помощника, адреса внутренних получателей и шесть назначений MAX. Не создавать production-тестовые запросы или сообщения. Проверки процесса выполняются на изолированной локальной базе с подменённым SMTP/IMAP/MAX; реальные сетевые операции тестами не выполняются.

## Помощник логиста после завершения рейса

Permission-key `company.documents.collection` также открывает компактное рабочее место `/company/logistics-assistant`; прежний сбор документов перевозчика остаётся доступен по прямой ссылке из рабочего места. В меню ключ называется «Помощник логиста», поэтому существующие grants не меняются.

Очередь строится только по завершённым рейсам отходов: рейсы отсортированы по номеру по убыванию, заявки внутри рейса — также по номеру по убыванию. По умолчанию включён фильтр «Скрывать полностью собранные». Дата и время загрузки вводятся одним цифровым полем `ДД.ММ.ГГ ЧЧ:ММ - ЧЧ:ММ`; дата уезда всегда берётся из даты приезда. Заявка считается собранной, когда указаны приезд и уезд с забора, подтверждены подписи водителя и отправителя и загружен хотя бы один активный скан ТН. В очереди и меню показывается фактическое количество незакрытых рейсов; поиск работает по рейсу, заявке, водителю и подрядчику.

Файлы хранятся в company-scoped каталоге и скачиваются с именем `Рейс_<номер>_Заявка_<номер>_ТН_<порядок>.<расширение>`; полное имя показывается в строке заявки. Счётчик файлов рейса обновляется сразу после загрузки и удаления без перезагрузки страницы. Удаление soft-delete возвращает заявку в очередь и сохраняет физический файл для аудита. По рейсу выдаются оформленный XLSX со всеми маршрутами, временем, подписями и проблемами, а также ZIP из этого XLSX и всех активных ТН.

Миграция `142_create_waste_trip_completion.sql` создаёт только две tenant-таблицы: факты комплектности и документы. GET не применяет DDL. Производственное применение выполняет manual-only workflow `trip_completion_142_production_migration.yml` после точного deploy canonical SHA, успешного CI и отдельного подтверждения `APPLY_TRIP_COMPLETION_142`; существующие рейсы и связи заявок сверяются хешами и не изменяются.
