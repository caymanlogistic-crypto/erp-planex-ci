# Рабочая почта сотрудника

В «Роли и доступы → Пользователи → карточка сотрудника» руководитель сохраняет
отдельный почтовый профиль для каждого настроенного юридического лица. Основной
`user_accounts.email` и прежние tenant emails не изменяются.

У каждого сотрудника два независимых почтовых профиля: «ПЛАНЭКС» (plan-ex.ru)
и «МГ-ЛОГ» (mg-log.ru). Названия хранятся в центральной таблице
`employee_mail_legal_entities` с кодами `planex` и `mg_log`. Это справочник компаний
для рабочей почты, не связанный с клиентами и подрядчиками. Он не создаёт tenants
или новые доступы. Существующий tenant задаёт границу доступа к профилям сотрудников.

Профиль уникален по `(account_id, company_id, legal_entity_id)`. Пароль защищён
AES-256-GCM существующим `APP_ENCRYPTION_KEY`; UI и JSON не получают ни пароль, ни
шифротекст. Пустое поле сохраняет прежний пароль, изменение адреса очищает прежний
секрет, явное удаление возвращает статус `incomplete`. Optimistic version запрещает
потерю параллельных изменений. Изменение секрета сбрасывает проверенный статус.

Общие настройки Spaceweb заданы в `EmployeeMailTransport`: IMAP
`imap.spaceweb.ru:993`, SMTP `smtp.spaceweb.ru:465`, SSL с проверкой сертификата,
логин — полный email. Источник: https://help.sweb.ru/nastrojka-pochtovyh-klientov_1240.html.
Проверка выполняет только подключение, аутентификацию и выход. Она не отправляет
писем, не открывает папки и не читает сообщения. Ошибки провайдера не журналируются.
`connected` устанавливается только при успешной проверке обоих протоколов.

## Контракт будущего «Запроса документов»

Раздел запросов в эту задачу не входит. Код будущего раздела создаёт
`EmployeeMailProfileService($centralPdo, $tenantPdo, $tenantCompanyId)` и вызывает
`resolve($accountId, $legalEntityId)` либо
`resolveEnvelope($senderAccountId, $legalEntityId, $assistantAccountId, $employeeAccountIds)`.
Результат содержит profile/account/tenant/legal-entity IDs, адрес отправителя,
адрес ПЛ в копии и адреса сотрудников этого же юрлица. Неподключённый профиль
возвращает понятную ошибку без fallback на основной email или другое юрлицо.
При создании будущей переписки необходимо закрепить эти IDs и адрес отправителя;
при ответе/напоминании/досылке использовать тот же legal_entity_id и проверять,
что адрес профиля не изменился. Секреты доступны только внутреннему transport-коду
через `credentials()`, не через HTTP. Отправка/чтение писем пока не реализуются.

## Ввод в работу

После signed LOCAL preflight, PR/CI/merge и memory PASS выполняется exact-SHA
guarded deploy, затем manual `employee_mail_016_production_migration.yml` с
`APPLY_CENTRAL_016_EMPLOYEE_MAIL`. Миграция создаёт только три центральные таблицы,
проверяет prerequisites/checksum/marker и сохраняет journal. Rollback разрешён
лишь пока новые таблицы пусты. Legacy `/erp` не используется.

OWNER 2026-09-20 отдельно разрешил production schema и заполнение шести профилей.
`scripts/employee_mail_setup.php inspect` сначала сопоставляет сотрудников по
существующим логинам (для Гладских допускается уникальная фамилия), существующий tenant ПЛАНЭКС по ИНН. `seed` принимает JSON паролей исключительно по stdin, с exact
deployed marker и `PLANEX_CONFIRM_MAIL=SETUP_SIX_PLANEX_MAIL_PROFILES`.
Пароли не передаются в аргументах или Git. У gladskih@mg-log.ru пароль остаётся
пустым. `check` проверяет остальные сохранённые профили без отправки писем.
