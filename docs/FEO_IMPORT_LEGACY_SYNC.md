# Импорт ФЭО: формат координат и старая база

Решение владельца от 18.09.2026: `/company/feo/requests` — единая точка ввода новых заявок. Разрешена узкая запись импортов в старую таблицу `feo`, включая отмену и возврат изменений соответствующей загрузки. Это исключение не разрешает менять код `/erp`, другие legacy-таблицы, массово выравнивать существующие реестры или переписывать старую историю.

## Формат файла

В окне загрузки новый формат выбран по умолчанию. Он содержит широту в Ш и долготу в Д; парсер один раз переставляет эти два значения перед анализом и сохранением. Старый формат сохраняется без перестановки. Существующий порядок БД остаётся: `mno_sh` — долгота, `mno_d` — широта. Остальные поля, карта и переносы сохраняют прежнюю семантику. Выбор хранится в серверном preview; commit не принимает замену формата из POST. Preview, созданные до выпуска, читаются как старый формат. Переключение радиокнопки повторяет анализ файла и заменяет токен подтверждения.

## Общая транзакция и границы

Поддержаны два режима. Shared использует tenant PDO и квалифицированное имя старой таблицы. Separate использует отдельный аккаунт старой БД: перекрёстные grants не требуются. Сохранение выполняет `FeoImportTransaction` через XA START/END/PREPARE/COMMIT на обоих соединениях. Два обычных независимых commit не используются. Нужны MySQL 5.7.7+ или MariaDB 10.5+, InnoDB, работоспособные XA и POSIX fsync. Проверяются необходимые столбцы, уникальные ключи, отсутствие триггеров и каскадных связей старой таблицы.

До первого XA START записывается durable abort intent, после обоих PREPARE — durable commit decision; решение синхронизируется на диск до подтверждения БД. Журнал вне web root: по умолчанию `dirname(BASE_PATH, 2)/feo-import-sync`, на текущем хостинге `/home/s/spugovxsim/planexp/feo-import-sync`; каталог 0700, файлы 0600, без паролей и данных заявок. Каталог должен сохраняться при deploy и восстановлении сервера. Настройка `FEO_LEGACY_SYNC_JOURNAL_DIR` предназначена только для серверной конфигурации. XA ID никогда не вводится пользователем, XA RECOVER и административные grants не нужны: восстанавливаются только известные собственные ID.

Ошибка до решения commit откатывает обе ветви. После решения commit откат запрещён: при обрыве подтверждения показывается незавершённая операция; следующая загрузка/история/проверка свежести сначала завершает сохранённое решение под FEO lock. Подготовленные ветви могут держать блокировки до восстановления связи. Отказ доступа или повреждённый журнал блокирует продолжение, не удаляя журнал. Мгновенная общая видимость двух COMMIT для сторонних читателей не обещается; после успешного ответа обе части подтверждены. Потеря ответа после подтверждения проверяется по истории и обычному file-hash guard.

Синхронизируются только реально добавленные/обновлённые этой загрузкой заявки. Пропавшие из файла заявки не удаляются. По умолчанию существующие заявки не перезаписываются в обеих базах. Если заявка новая для ERP, но уже есть в старой БД, без явной перезаписи её прежняя legacy-строка сохраняется и откат её не удаляет. При перезаписи сохраняются legacy-only столбцы. Активные переносы защищают местоположение; у существующей старой заявки импорт не меняет три поля места при активном tenant-переносе. Ручные карточки, размещение, поездки и очередь переносов не являются частью этого зеркала импортов.

В `feo_import_changes.after_json` добавляется зарезервированный ключ `__legacy_import_sync` с версией, точной схемой назначения и полными legacy-снимками до/после. Бизнес-снимок новой ERP остаётся на прежнем уровне JSON. Миграция, новый столбец, новая таблица и изменение существующих координат не требуются. Старые загрузки без этого ключа работают по прежнему tenant-журналу: реконструировать отсутствующие legacy before-images автоматически нельзя.

Откат и возврат используют сохранённые legacy-снимки, а не текущий XLSX и не значения другой БД. У новой legacy-строки при возврате восстанавливается прежний PK. Существующие строки и timestamps восстанавливаются точно. Проверяется вся legacy-строка: последующая ручная правка останавливает операцию в обеих базах. Пропущенная при импорте старая строка не принадлежит загрузке и не блокируется её независимыми правками. Удаление применённой загрузки сначала выполняет тот же откат; удаление уже отменённой истории не затрагивает legacy.

Решение владельца от 18.09.2026: все импортируемые значения приводятся к вместимости старых полей только при записи legacy-копии. VARCHAR/CHAR обрезаются справа по количеству символов; TEXT дополнительно ограничивается байтовой вместимостью без разрыва UTF-8. У DECIMAL лишние дробные знаки отбрасываются к нулю без округления. Выход за диапазон DECIMAL/целого ограничивается ближайшей допустимой границей, с учётом UNSIGNED. Ограничения читаются из реальной схемы старой таблицы, а не задаются отдельно для статуса. Например, 59-символьный статус сохраняется полностью в новой базе и первыми 50 символами в старом VARCHAR(50). Новая ERP хранит исходные значения в рамках своего действующего парсера и схемы. Схемы баз не меняются.

Идентификатор zayavka_id должен оставаться тем же в обеих базах: изменение номера при приведении запрещено, чтобы не подменить заявку. Неверные типы/даты, конфликты, отсутствие доступа и прочие ошибки не маскируются обрезанием. Журнал содержит фактически сохранённые legacy-значения; откат восстанавливает точное прежнее состояние, возврат — уже приведённые значения без повторного расчёта.

## Включение

Две настройки приложения связывают одну конкретную компанию и legacy-схему:

```
FEO_LEGACY_SYNC_TENANT_DATABASE=<точное имя tenant-БД>
FEO_LEGACY_SYNC_DATABASE=spugovxsim_frega
```

У пользователя, которым открыта старая БД (tenant в shared или отдельный legacy в separate), необходимы SELECT, INSERT, UPDATE, DELETE на `spugovxsim_frega.feo`, а также TRIGGER для достоверной проверки наличия триггеров. Credentials `LEGACY_FLIGHTS_DB_*` остаются read-only и для записи не используются. Другие компании не получают доступ к старой БД через этот механизм. Параметры берутся только из серверной конфигурации, не из пользовательского POST.

Guarded workflow `FEO Import Sync Configuration` запускается только после exact canonical CI и соответствующего deploy. `check` с `company_id=0` выводит active company inventory без паролей; с точным ID проверяет доступ и совместимость без записи данных. `activate` требует точный ID, сохраняет защищённую резервную копию `.env` и добавляет привязку баз, а в separate — защищённую настройку подключения. Существующее отличающееся назначение не заменяет. Workflow не выдаёт MySQL-права. В режиме separate используются предоставленные владельцем реквизиты существующего аккаунта старой БД из GitHub secret `FEO_LEGACY_SYNC_CONNECTION` (JSON host/port/username/password); secret передаётся только через stdin SSH и сохраняется в защищённом .env как `FEO_LEGACY_SYNC_CONNECTION_B64`. Base64 является кодировкой, а не шифрованием; доступ к .env и его backup должен оставаться закрытым. Read-only readiness проверяет также XA prepare/commit без пробных записей. Секреты не передаются в inputs/argv/логи. Проверка не создаёт пробные production-заявки.

До настройки окно загрузки и итог импорта явно сообщают об отсутствии синхронизации. Уже синхронизированную загрузку нельзя откатить только в новой БД, удалив настройки: её журнал требует доступного прежнего назначения. Для смены назначения или отключения после использования необходим отдельный план миграции истории.

## Точечное изменение веса для операций ERP

`FeoImportTransaction::runWithLegacy($tenantPdo, $callback)` выполняется вызывающей операцией под общим FEO lock. Метод завершает ожидающее XA-решение, начинает общую транзакцию, проверяет старую таблицу, передаёт в callback подготовленный `FeoLegacyImportSync` и подтверждает обе базы. Исключение до решения commit откатывает обе ветви; после durable commit decision сохранённый XA-журнал завершается следующей операцией. Существующий путь импорта не изменён.

`FeoLegacyImportSync::writeWeight($zayavkaId, ['mass_netto'=>..., 'mass_brutto'=>...])` меняет только два поля по уникальному `zayavka_id` и возвращает `version`, `database`, `zayavka_id`, `before`, `after`. `before` и `after` содержат **фактические значения старой таблицы**, с точностью её DECIMAL; полные значения ERP могут иметь другую точность. Отсутствующая заявка останавливает общую транзакцию. Полученный снимок следует сохранять в журнале вызывающей ERP-операции в той же транзакции.

`revertWeight($zayavkaId, $snapshot)` сверяет обе текущие legacy-массы со снимком `after`, восстанавливает только `before` и возвращает обратный снимок. Поздняя правка массы, другой ID или другая привязка базы останавливают возврат без изменения бизнес-данных. Вызывающая операция отдельно проверяет актуальность ERP-заявки и своего журнала. Весовые блоки вызывают эти методы под FEO lock и хранят независимые снимки в `feo_weight_items.legacy_snapshot_json` после миграции 162.

- `tests/feo_legacy_import_sync_mysql_test.php`: apply/rollback/restore/delete, LIFO, точные legacy before-images, сохранность чужих строк/полей, конфликты, атомарность поздней ошибки, schema guards, обрезание Unicode/байтов TEXT, точность/границы signed и unsigned чисел, сохранность полных tenant-значений и привязка tenant. - Существующие контракты ФЭО и MySQL-проверки переносов остаются обязательными.

- `tests/feo_legacy_xa_mysql_test.php`: весь import contract через отдельные соединения, восстановление после первого commit, ошибка prepare, исчезновение процесса после одного prepare, повреждённый journal. Дополнительная локальная проверка использует два аккаунта с правами строго на свои две disposable-схемы.
- `tests/feo_legacy_weight_bridge_xa_mysql_test.php`: запись и возврат двух масс, фактическая точность старой схемы, поздний конфликт, отсутствующая строка и восстановление durable решения после обрыва между подтверждениями баз.
