# Импорт ФЭО: формат координат и старая база

Решение владельца от 18.09.2026: `/company/feo/requests` — единая точка ввода новых заявок. Разрешена узкая запись импортов в старую таблицу `feo`, включая отмену и возврат изменений соответствующей загрузки. Это исключение не разрешает менять код `/erp`, другие legacy-таблицы, массово выравнивать существующие реестры или переписывать старую историю.

## Формат файла

В окне загрузки новый формат выбран по умолчанию. Он содержит широту в Ш и долготу в Д; парсер один раз переставляет эти два значения перед анализом и сохранением. Старый формат сохраняется без перестановки. Существующий порядок БД остаётся: `mno_sh` — долгота, `mno_d` — широта. Остальные поля, карта и переносы сохраняют прежнюю семантику. Выбор хранится в серверном preview; commit не принимает замену формата из POST. Preview, созданные до выпуска, читаются как старый формат. Переключение радиокнопки повторяет анализ файла и заменяет токен подтверждения.

## Общая транзакция и границы

Обе схемы должны находиться на одном MySQL-сервере. `FeoLegacyImportSync` использует PDO текущей tenant-БД и квалифицированное имя старой таблицы в той же транзакции. Новая независимая сессия к старой базе не открывается: раздельные commit не обеспечили бы атомарность. Проверяются InnoDB всех четырёх таблиц, необходимые столбцы, уникальность PK и business key, отсутствие триггеров и каскадных внешних связей старой таблицы. При ошибке вся операция откатывается. Потеря ответа после COMMIT не означает откат: повторная загрузка того же файла блокируется обычным file-hash guard, состояние проверяется в истории.

Синхронизируются только реально добавленные/обновлённые этой загрузкой заявки. Пропавшие из файла заявки не удаляются. По умолчанию существующие заявки не перезаписываются в обеих базах. Если заявка новая для ERP, но уже есть в старой БД, без явной перезаписи её прежняя legacy-строка сохраняется и откат её не удаляет. При перезаписи сохраняются legacy-only столбцы. Активные переносы защищают местоположение; у существующей старой заявки импорт не меняет три поля места при активном tenant-переносе. Ручные карточки, размещение, поездки и очередь переносов не являются частью этого зеркала импортов.

В `feo_import_changes.after_json` добавляется зарезервированный ключ `__legacy_import_sync` с версией, точной схемой назначения и полными legacy-снимками до/после. Бизнес-снимок новой ERP остаётся на прежнем уровне JSON. Миграция, новый столбец, новая таблица и изменение существующих координат не требуются. Старые загрузки без этого ключа работают по прежнему tenant-журналу: реконструировать отсутствующие legacy before-images автоматически нельзя.

Откат и возврат используют сохранённые legacy-снимки, а не текущий XLSX и не значения другой БД. У новой legacy-строки при возврате восстанавливается прежний PK. Существующие строки и timestamps восстанавливаются точно. Проверяется вся legacy-строка: последующая ручная правка останавливает операцию в обеих базах. Пропущенная при импорте старая строка не принадлежит загрузке и не блокируется её независимыми правками. Удаление применённой загрузки сначала выполняет тот же откат; удаление уже отменённой истории не затрагивает legacy.

В старой схеме числовые и текстовые поля местами короче. Данные, которые не помещаются без округления/обрезания, отклоняются с ID заявки и полем. Схема не расширяется автоматически.

## Включение

Две настройки приложения связывают одну конкретную компанию и legacy-схему:

```
FEO_LEGACY_SYNC_TENANT_DATABASE=<точное имя tenant-БД>
FEO_LEGACY_SYNC_DATABASE=spugovxsim_frega
```

У PDO-пользователя этой tenant-БД необходимы SELECT, INSERT, UPDATE, DELETE на `spugovxsim_frega.feo`, а также TRIGGER для достоверной проверки наличия триггеров. Credentials `LEGACY_FLIGHTS_DB_*` остаются read-only и для записи не используются. Другие компании не получают доступ к старой БД через этот механизм. Параметры берутся только из серверной конфигурации, не из пользовательского POST.

Guarded workflow `FEO Import Sync Configuration` запускается только после exact canonical CI и соответствующего deploy. `check` с `company_id=0` выводит active company inventory без паролей; с точным ID проверяет доступ и совместимость без записи данных. `activate` требует точный ID, сохраняет защищённую резервную копию `.env` и добавляет только эти две настройки. Существующее отличающееся назначение не заменяет. Workflow не выдаёт MySQL-права: при их отсутствии администратор хостинга должен настроить доступ отдельно. Проверка не создаёт пробные production-заявки.

До настройки окно загрузки и итог импорта явно сообщают об отсутствии синхронизации. Уже синхронизированную загрузку нельзя откатить только в новой БД, удалив настройки: её журнал требует доступного прежнего назначения. Для смены назначения или отключения после использования необходим отдельный план миграции истории.

## Локальная проверка

- `tests/feo_legacy_import_sync_mysql_test.php`: apply/rollback/restore/delete, LIFO, точные legacy before-images, сохранность чужих строк/полей, конфликты, атомарность поздней ошибки, schema/precision guards и привязка tenant. Дополнительный `PLANEX_TEST_LEGACY_DB` позволяет проверить две отдельные disposable-схемы с включением обеих в тестовый allowlist.
- `tests/feo_xlsx_parser_format_test.php`: оба порядка, остальные поля неизменны, неполная пара и неверное значение формата.
- `tests/feo_import_browser_test.mjs`: настоящий Chromium, desktop/mobile, radio default, multipart с файлом и повторный анализ. Только синтетические browser endpoint responses.
- `tests/feo_legacy_sync_configuration_test.php`: сохранность настроек, идемпотентность, отказ при смене/дублировании назначения и activation guards.
- Существующие контракты ФЭО и MySQL-проверки переносов остаются обязательными.
