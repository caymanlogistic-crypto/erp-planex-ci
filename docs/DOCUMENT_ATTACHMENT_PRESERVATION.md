# Сохранность вложений исполнителя и ограниченное восстановление

## Действующий контракт

Файл — отдельный элемент, а не один элемент на HTML-контрол. `captureDraft` сохраняет все элементы FileList и индекс **контрола** для последующего открытия. При открытии черновика файлы группируются по реальному контролу, FileList назначается один раз. При сборке PHP input терминальный `[]` означает добавление в порядке исходного списка; повторный исторический индекс контрола не должен перезаписывать соседний файл. Для пользовательских строк с неявным [] индекс означает строку подписи и сохраняется, включая пустые предыдущие строки. Явно заданные пользовательские индексы сохраняются, неоднозначная скалярная коллизия отклоняется.

Для стандартных документов русская подпись берётся из `TripDocumentPackage::LABELS`. Технические `passport`, `driver_license`, `snils`, `company_card` — коды, а не видимые названия. Пользовательские типы и оригинальные имена загруженных файлов сохраняются. Дизайн не разрешает менять состав вложений, имена, ссылки, права или сценарии сохранения.

`tools/document_attachment_checks.py` — общий исполняемый набор LOCAL и CI: исторические индексы, серверный перенос, сохранность существующих документов и ограничение доступа, реальный browser FileList → multipart → cards.save → повторное открытие/сохранение → materialization с disposable MySQL, а также защитные проверки восстановления. Отсутствующий тест, данные или падение блокируют выпуск. Источники привязаны к `document_attachments` в `ci_scope.py`; финальный LOCAL publisher вызывает тот же набор. CI regression срабатывает по этим путям независимо от класса UI изменения.

## OWNER-разрешённое восстановление 20.10.2026

Отдельный manual workflow `document_attachment_recovery_production.yml` работает только с canonical и точным deployed SHA. Он не запускается на push/PR и не является общей миграцией. Разрешение: добавить 37 подтверждённых отсутствующих файлов компании 25, вернуть 74 русские подписи и привязать их к четырём уже существующим согласованным типам; существующие файлы не заменять. Шесть неопределённых исторических почтовых версий в эту операцию не входят.

Canonical recovery CLI и его read-only inspector передаются как административные инструменты в новый каталог `/tmp/planex-attachment-recovery-<run>-<attempt>`; их SHA проверяются, владелец отмечается source SHA, после операции удаляются только эти файлы/каталог. Рабочий код приложения не подменяется. `PLANEX_ROOT` всегда указывает на штатный `/erpv2`; payload идёт по stdin, на сервер не сохраняется. Изменение только этого инструмента не требует повторной выкладки всего приложения. Подавленные ожидаемые предупреждения безопасного filesystem probe (`@stat` исчезнувшего `/proc/self/fd`) не превращаются в исключение; отсутствие файла/ссылка по-прежнему дают отказ, неподавленные I/O ошибки скрываются общим безопасным кодом. Pure IO test и MySQL recovery test устанавливают тот же handler, что production CLI; Linux CI проверяет реальный `/proc`.

Частный конечный план содержит baseline, source metadata/hash, целевую карточку и сохранившийся документ той же сущности. 35 источников читаются из сохранённых review-файлов, ещё 2 PNG предоставлены OWNER. Имена последних двух описывают стороны документа; их утраченные исторические имена неизвестны.

У каждого review-источника обязательно задана точная историческая `source_identity` из последнего применимого контрола исходной формы. Она проверяется отдельно от текущей сущности: законное исправление ФИО/номера после анкеты не означает другого владельца. Текущая сущность по-прежнему точно совпадает с baseline, а сохранившийся reference подтверждает entity ID, тип и SHA. Fuzzy-сопоставление запрещено; историческое значение не записывается в действующую карточку. У двух OWNER-источников этот ключ запрещён. Read-only export включает только адресные name/full_name/plate_number в своих формах, сохраняя порядок и fingerprint полного исходного JSON; паспортные номера/телефоны и посторонние формы исключены. Общий LOCAL/CI набор исполняет и этот privacy-контракт.

1. План и копии остаются в закрытом task evidence. Для передачи используется только зашифрованный файл в временном **draft** release; ключ — отдельный временный Actions secret, локальная копия защищена DPAPI. GitHub скрывает draft release от токена `contents: read`; необходимый `contents: write` выдан только этому ручному canonical-only job. На PR/push он не запускается. Ciphertext SHA и plaintext SHA проверяются независимо. В Git, PR, Notion и Actions logs персональные данные и файлы не попадают.
2. `check` проверяет baseline, entity/source/reference, хеши и отсутствие замены. Возвращает зашифрованный before-image и digest. Координатор сохраняет и проверяет его до `apply`.
3. `apply` принимает этот digest, повторяет проверки под блокировкой и транзакцией. Новые файлы создаются исключительно через `xb` с новыми случайными именами. Старые файлы не переписываются. Повторное применение не создаёт дубликатов по entity/content SHA. ID документов, файлы, связи сущностей и права сохраняются. Только у 74 согласованных записей технический type ID заменяется существующим русским типом с теми же code/entity_type. Все 33 строки каталога сохраняются: четыре технические строки не переименовываются в конфликт с UNIQUE и не удаляются. Новые строки явно принадлежат административному восстановлению, а не исходному загрузчику.
4. При подтверждённом rollback удаляются только созданные данной операцией файлы. При неизвестном результате COMMIT файлы сохраняются до новой проверки. Подтверждённый apply проверяется независимым read-only inventory и доступностью документов в приложении. Временные secret/transport удаляются после сохранения доказательств.

До merge проверять тестами GREEN и RED: неверный hash, неподтверждённая сущность, drift baseline, rollback, повторный запуск, сохранность старых файлов и отказ при неоднозначности. Production не используется для разработки или подбора payload. Расхождение в `check` — остановка до записи, затем ограниченная диагностика.
