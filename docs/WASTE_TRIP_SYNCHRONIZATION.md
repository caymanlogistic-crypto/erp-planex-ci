# Синхронизация рейсов со старой БД

## Поведение

На `company/trips/departures` руководителю компании доступна кнопка синхронизации.
При каждом открытии реестра выполняется контрольная сверка ID и статусов рейсов `flights.id > 225` со связанными и видимыми рейсами ERP. Жёлтое предупреждение показывает оба количества, номера отсутствующих рейсов, номера рейсов с несовпадающим статусом и с последней ошибкой синхронизации. Причина ошибки доступна в карточке рейса. Самостоятельные рейсы ERP показываются отдельно и в сопоставление не входят. Если источник недоступен, страница сообщает, что сверка не выполнена.
Ручной каталог и форма импорта, их маршруты и сервис предварительного заполнения удалены.
Синхронизация читает полный список `flights.id > 225` через соединение старой БД только для чтения.
Создаёт отсутствующие рейсы и обновляет ранее импортированные, сохраняя внутренний ID и номер старого рейса.
Самостоятельные рейсы ERP не присваиваются синхронизацией; конфликт номера или заявки с таким рейсом отражается в результате.

| Старая БД | Новая ERP |
|---|---|
| `id` | `business_id`, `legacy_flight_id`; источник `legacy_sync` |
| `zayavki_ids` | Состав заявок ФЭО, порядок, снимок массы; повторы между синхронизируемыми рейсами разрешены |
| `comment` | Описание |
| `planned_start_date`, `planned_start_date_from/to` | Точная дата, закрытый или открытый диапазон, либо дата не указана |
| `actual_start_date`, `actual_end_date` | Фактическое начало и окончание |
| `status` | `planned_route/search/attention` → Планируемый; `found` → Сформированный; `started` → Вывоз начался; `completed` → Груз сдан |
| `cost` | ПРОДАЖА: сумма для взаиморасчётов с клиентом; NULL, ноль и 1 различаются |
| `status_blocks` + `feo.mass_netto` | ГЕН. ЗАКАЗЧИК: сумма по заявкам, рассчитанная по legacy `include/price.php` |
| `assigned_manager_id` → `users.Фамилия` | Первое слово имени активного пользователя компании; совпадение должно быть единственным |
| `driver_id` → `drivers.full_name`, `vehicle_make_plate` | Единственный активный исполнитель по первому слову фамилии и полному номеру тягача с регионом |
| `unload_type` | `SKLAD` → склад; `OO` → утилизатор, определяемый по получателю заявок ФЭО |

Заказчик определяется по единственному активному клиенту ООО «МГ ЛОГИСТИК» в новой ERP.
Числовые ID заказчика, менеджера и исполнителя не зашиты в код.
Подтверждённое владельцем отличие написания «Гладских Карина» → «Гладких» учитывается до поиска по фамилии.
Неоднозначный или отсутствующий менеджер останавливает обновление этого рейса.
Нераспознанный исполнитель или утилизатор остаётся незаполненным с пояснением; новые справочники автоматически не создаются.
Если исполнитель (подрядчик/водитель) связанного рейса был вручную назначен в ERP, дальнейшая синхронизация сохраняет последний ручной выбор, даже если исполнитель в старой БД меняется или исчезает. Ручной выбор определяется по аудиту изменений рейса, включая сохранения до введения явного признака `executor_sync_disabled`; новые успешные изменения фиксируют этот признак в том же аудите. Неудачное или устаревшее сохранение не меняет владельца поля. Без ручного выбора исполнитель продолжает сопоставляться со старой БД.
Неизвестные статус, дата, назначение, некорректная стоимость или отсутствующая заявка останавливают обновление соответствующего рейса.

Фоновая синхронизация связанного рейса переносит статус и полный текущий состав заявок из `flights` при каждом успешном проходе. Ручная синхронизация использует тот же принцип. Статус `started` или `completed` переносится даже при отсутствии фактических дат в старой записи; даты остаются пустыми. Исключённая из источника заявка получает `waste_trip_requests.removed_at`; строка и её ID сохраняются для журнала регистрации и документов. Текущие списки, суммы, складские расчёты и проверка занятости учитывают только связи без `removed_at`. Если заявка вернулась в исходный рейс, прежняя строка активируется с тем же ID. Миграция `158_waste_trip_request_archival.sql` добавляет признак архивации без изменения бизнес-данных; до её применения готовность реестра не подтверждается.

## Оплаты и удаление

ГЕН. ЗАКАЗЧИК хранится отдельно и не создаёт обязательства во взаиморасчётах. ПРОДАЖА создаёт RECEIVABLE клиенту, ручная СЕБЕС — PAYABLE подрядчику. ГЕН. ЗАКАЗЧИК обновляется при каждой синхронизации и доступен только для чтения. ПРОДАЖА синхронизируется до первого ручного изменения суммы и успешного сохранения рейса; после этого сумма данного рейса остаётся под управлением ERP. Изменение только условий оплаты, сохранение той же суммы (включая другой числовой формат) и несохранённое/отклонённое изменение не отключают синхронизацию. Условия оплаты можно редактировать. Себестоимость синхронизация не записывает.

Цена генерального заказчика: только `status_blocks.status_type=marshrut` с положительной стоимостью; вес положительных заявок берётся из legacy `feo`. Стоимость распределяется пропорционально весу с округлением вниз до целого рубля у всех, кроме первой самой тяжёлой заявки: ей отдаётся остаток. Вхождение в несколько блоков суммируется. Если хотя бы у одной заявки нет цены, итог неизвестен (NULL), а не частичная сумма.

По умолчанию ГЕН. ЗАКАЗЧИК/ПРОДАЖА — after_end, 3 календарных дня; СЕБЕС — after_end, 7 календарных дней. Ручные условия сохраняются при изменении суммы, исчезновении и возврате цены. NULL и ноль различаются. До фактической выгрузки финансовый срок ожидает событие; плановая дата остаётся прогнозом.

При совпадении общей суммы сохраняется разбивка. При изменении суммы сохраняются первая строка и её условия. Удаление других частей или исчезновение цены запрещено при связях со счетами/проведёнными оплатами. Способ оплаты и НДС источника не выдумываются; legacy payment_terms хранится комментарием. Факты оплат не удаляются.

Рейс, отсутствующий в полном успешно прочитанном снимке старой БД, получает `deleted_at` и статус отмены, скрывается из списка и карточек.
Руководитель может вручную удалить из карточки обычный или отменённый рейс. Это мягкое удаление: рейс скрывается, заявки освобождаются, а аудит, документы и финансовые факты сохраняются. Проверка версии защищает от удаления устаревшей формы. Вручную удалённый связанный рейс не восстанавливается следующей синхронизацией и остаётся виден в контрольной сверке как отсутствующий в ERP.
Его связи, аудит и проведённые оплаты сохраняются, обычные обязательства модели 2 отменяются. Исторические обязательства модели 3 сохраняются для расчётов по реальным счетам и оплатам. Повторное появление восстанавливает тот же рейс.
Ошибка чтения источника никогда не используется как пустой список для удаления.
Удаление применяется только к подтверждённым источникам `legacy_flights`, `legacy_prefill`, `legacy_sync` с `business_id = legacy_flight_id > 225`.

Отключение синхронизации продажи хранится как `customer_amount_sync_disabled: true` в существующем неизменяемом `waste_trip_audit_log.after_json` действия `update`, в одной транзакции с ручным изменением. Синхронизация проверяет наличие этого события для данного рейса, а не последнее событие: последующие сохранения и удаление/восстановление из источника не включают её обратно. Аудит является долговечным источником этого признака (как и сохранённых расчётов модели 3), его нельзя очищать. Новая схема или backfill не требуются. Генеральная сумма, состав, даты и остальные поля продолжают обновляться; правила сохранённых расчётов модели 3 не меняются.

Каждый рейс обрабатывается в собственной транзакции; ошибка откатывает его состав, стоимость и аудит.
Общая блокировка MySQL не допускает одновременный запуск кнопки и прежнего задания синхронизации.
Пользователь получает количество созданных, обновлённых, удалённых рейсов и ошибки по номерам.

## Запуск и выпуск

Кнопка выполняет синхронизацию по запросу. Существующее задание хостинга каждые пять минут продолжает прежнее обновление только `legacy_flights`.
После обработки кнопкой источник меняется на `legacy_sync`; дальнейшее полное обновление таких рейсов выполняется кнопкой.
Новое расписание и задания GitHub Actions не добавлены.

Предыдущий этап синхронизации использует миграцию `137_waste_trip_synchronization.sql`: добавление статуса `planned_route`, nullable `deleted_at` и индекса.
Миграция не запускает синхронизацию и не меняет бизнес-данные. Её production-применение требует отдельного разрешения владельца согласно AGENTS.md.
Подготовлен guarded workflow с проверками точного SHA, контрольной суммы, журналирования, схемы и неизменности существующих данных до/после.
Откат приложения не требует удаления новых столбцов; автоматическое разрушительное обратное преобразование данных не предусмотрено.

## Проверки кандидата

`waste_trip_legacy_mapping_test.php`: фамилии, подтверждённый вариант написания, неоднозначность, номера машин, статусы, даты, стоимости.

`waste_trip_synchronization_mysql_test.php`: полная схема MySQL, повторный запуск, обновление старых импортов, повторы заявок, оплата, разбивка стоимости, откат при сбоях, удаление/восстановление, граница ID и независимые рейсы, доступ и блокировка.

`waste_trip_regression_test.php`: самостоятельные рейсы, конкурентная выдача номеров, прежний планировщик.

`waste_trips_137_migration_mysql_test.php`: реальные apply/verify-скрипты, повторное применение, сохранность данных и отказ при неверной контрольной сумме.

Дополнительно сохраняются проверки финансов перевозчика/заказчика, проекции менеджеров, маршрутов и интерфейса, а также обязательный CRITICAL preflight и CI.

## Реестр — согласованный контракт 2026-09-16

- По умолчанию рейсы сортируются по статусу в порядке «Планируемый», «Сформированный», «Вывоз начался», «Груз сдан», «Отменён»; внутри статуса новые ID идут первыми. Сортировка по ID и по менеджеру доступна вручную, «Сбросить» возвращает порядок по статусу.
- 12 колонок: ID, описание, начало, окончание, статус, подрядчик/водитель, количество заявок, суммарный вес, менеджер, ГЕН. ЗАКАЗЧИК, ПРОДАЖА, СЕБЕС.
- ID/описание/статус не переносятся; длинное описание сокращается с полной подсказкой и полным текстом в карточке. Узкое окно прокручивает только таблицу.
- Даты как в линейном реестре: факт приоритетен, иначе серый план с подписью; отсутствие обозначается прочерком. Открытые/полные диапазоны источника сохраняются. Отдельной красной подсветки просрочки нет, как и в текущем линейном реестре.
- Четыре выбираемых статуса: планируемый (системный фиолетовый), сформированный (бирюзовый), вывоз начался (зелёный), груз сдан (серый). Цвет занимает ячейку. Исторический searching_executor отображается/фильтруется как planned_route без backfill; cancelled остаётся внутренним историческим состоянием отмены/удаления и не предлагается в форме.
- Исполнитель: подрядчик, фамилия с инициалами водителя, машина отдельными строками. Пустой driver_id источника — прочерк без предупреждения. Указанный, но несопоставленный исполнитель — системная жёлтая ячейка «не нашлось соответствия с новой базой»; отдельные предупреждения утилизатора не подсвечивают исполнителя.
- Количество/вес берутся по всему составу рейса, включая поиск по одной заявке. Менеджер: имя и первая буква фамилии.
- Три стоимости показывают итог и условия оплаты, прочерк при неизвестной сумме. Финансовый доступ остаётся только в finance realm. Колонка доходности удалена.
- При выгрузке на склад генеральный заказчик не оплачивает рейс: его ячейка серая и пустая, поля оплаты скрыты и отключены, подменённая отправка стоимости отвергается сервером. Существующие исторические суммы остаются в БД для аудита; продажа клиенту и себестоимость рейса работают по прежним правилам.

## Переход на три суммы (138)

Миграция `138_waste_trip_general_payments.sql` добавляет отдельный график генерального заказчика, nullable сумму клиента и версию финансовой модели. SQL не переносит бизнес-данные. Отдельный `WasteTripFinancialTransitionService` транзакционно переносит прежнюю продажу в генерального заказчика, прежнюю себестоимость в продажу, оставляет новую себестоимость пустой и фиксирует аудит. Уже заданные сроки сохраняются; отсутствующие получают 3 дня. Повторный запуск безопасен, включая продолжение после уже применённой и записанной в журнал схемы 138.

По согласованию OWNER реальные счета и оплаты сохраняются. Рейс со связью обязательства со счётом либо с активным распределением проведённой оплаты получает модель 3: прежние обязательства, их суммы, сроки, идентификаторы и связи сохраняются. Последующие оплаты и отмены оплат обновляют их оплаченный остаток и статус. Три новые суммы такого рейса справочные и не создают дополнительные долги; это явно указано в реестре и карточке для пользователей финансового раздела. Документы клиенту используют исходный график из аудита перехода, а при отсутствии этого графика отказывают в формировании. Рейсы без финансовых связей получают модель 2 и обычные обязательства по новой продаже и ручной себестоимости.

`scripts/waste_trips_compare_138.py` проверяет фактический перенос для каждого рейса по версии модели, в том числе при повторном запуске и смешанном состоянии tenant. Связанные обязательства, счета, операции и распределения должны остаться неизменными. MySQL-регрессия запускает этот же production-компаратор и проверяет отказ при подмене перенесённой суммы или исторического обязательства.

Production workflow `waste_trips_138_production_migration.yml` требует отдельного разрешения OWNER именно на схему и перенос сумм, exact canonical + CI, сериализацию с deploy, before/after snapshots, неизменность операций, allocations, счетов и связей. Manifest указывает 138; это готовность механизма, а не разрешение на его запуск. До разрешения production БД не меняется. Перенос выполняется через штатный control plane, затем публикуется соответствующий код.
