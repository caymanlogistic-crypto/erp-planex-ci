# Синхронизация рейсов со старой БД

## Поведение

На `company/trips/departures` руководителю компании доступна кнопка синхронизации.
Ручной каталог и форма импорта, их маршруты и сервис предварительного заполнения удалены.
Синхронизация читает полный список `flights.id > 225` через соединение старой БД только для чтения.
Создаёт отсутствующие рейсы и обновляет ранее импортированные, сохраняя внутренний ID и номер старого рейса.
Самостоятельные рейсы ERP не присваиваются синхронизацией; конфликт номера или заявки с таким рейсом отражается в результате.

| Старая БД | Новая ERP |
|---|---|
| `id` | `business_id`, `legacy_flight_id`; источник `legacy_sync` |
| `zayavki_ids` | Состав заявок ФЭО, порядок, снимок массы; повторы между синхронизируемыми рейсами разрешены |
| `comment` | Описание |
| `planned_start_date`, `planned_start_date_from/to` | Точная дата, закрытый или открытый диапазон, либо дата не указана |
| `actual_start_date`, `actual_end_date` | Фактическое начало и окончание |
| `status` | `planned_route/search/attention` → Планируемый; `found` → Сформированный; `started` → Вывоз начался; `completed` → Груз сдан |
| `cost` | Общая стоимость оплаты перевозчику; NULL, ноль и 1 различаются |
| `assigned_manager_id` → `users.Фамилия` | Первое слово имени активного пользователя компании; совпадение должно быть единственным |
| `driver_id` → `drivers.full_name`, `vehicle_make_plate` | Единственный активный исполнитель по первому слову фамилии и полному номеру тягача с регионом |
| `unload_type` | `SKLAD` → склад; `OO` → утилизатор, определяемый по получателю заявок ФЭО |

Заказчик определяется по единственному активному клиенту ООО «МГ ЛОГИСТИК» в новой ERP.
Числовые ID заказчика, менеджера и исполнителя не зашиты в код.
Подтверждённое владельцем отличие написания «Гладских Карина» → «Гладких» учитывается до поиска по фамилии.
Неоднозначный или отсутствующий менеджер останавливает обновление этого рейса.
Нераспознанный исполнитель или утилизатор остаётся незаполненным с пояснением; новые справочники автоматически не создаются.
Неизвестные статус, дата, назначение, некорректная стоимость или отсутствующая заявка останавливают обновление соответствующего рейса.

## Оплаты и удаление

При совпадении общей стоимости сохраняется существующий график оплаты. У единственной оплаты обновляется сумма с сохранением её условий и идентичности.
При изменении общей стоимости нескольких оплат они объединяются в одну без выдуманных сроков, способа и НДС.
Объединение запрещено, если удаляемая часть графика связана со счётом или проведённой оплатой; весь рейс сохраняет прежнее состояние и выводится ошибка.
Новая стоимость без графика создаётся с неизвестными условиями; `payment_terms` сохраняется комментарием.
Ставка и условия оплаты заказчика сохраняются. Финансовые обязательства пересчитываются штатным сервисом, факты платежей не удаляются.

Рейс, отсутствующий в полном успешно прочитанном снимке старой БД, получает `deleted_at` и статус отмены, скрывается из списка и карточек.
Его связи, аудит и проведённые оплаты сохраняются, обязательства отменяются. Повторное появление восстанавливает тот же рейс.
Ошибка чтения источника никогда не используется как пустой список для удаления.
Удаление применяется только к подтверждённым источникам `legacy_flights`, `legacy_prefill`, `legacy_sync` с `business_id = legacy_flight_id > 225`.

Каждый рейс обрабатывается в собственной транзакции; ошибка откатывает его состав, стоимость и аудит.
Общая блокировка MySQL не допускает одновременный запуск кнопки и прежнего задания синхронизации.
Пользователь получает количество созданных, обновлённых, удалённых рейсов и ошибки по номерам.

## Запуск и выпуск

Кнопка выполняет синхронизацию по запросу. Существующее задание хостинга каждые пять минут продолжает прежнее обновление только `legacy_flights`.
После обработки кнопкой источник меняется на `legacy_sync`; дальнейшее полное обновление таких рейсов выполняется кнопкой.
Новое расписание и задания GitHub Actions не добавлены.

До выкладки приложения нужна отдельная миграция `137_waste_trip_synchronization.sql`: добавление статуса `planned_route`, nullable `deleted_at` и индекса.
Миграция не запускает синхронизацию и не меняет бизнес-данные. Её production-применение требует отдельного разрешения владельца согласно AGENTS.md.
Подготовлен guarded workflow с проверками точного SHA, контрольной суммы, журналирования, схемы и неизменности существующих данных до/после.
Откат приложения не требует удаления новых столбцов; автоматическое разрушительное обратное преобразование данных не предусмотрено.

## Проверки кандидата

`waste_trip_legacy_mapping_test.php`: фамилии, подтверждённый вариант написания, неоднозначность, номера машин, статусы, даты, стоимости.

`waste_trip_synchronization_mysql_test.php`: полная схема MySQL, повторный запуск, обновление старых импортов, повторы заявок, оплата, разбивка стоимости, откат при сбоях, удаление/восстановление, граница ID и независимые рейсы, доступ и блокировка.

`waste_trip_regression_test.php`: самостоятельные рейсы, конкурентная выдача номеров, прежний планировщик.

`waste_trips_137_migration_mysql_test.php`: реальные apply/verify-скрипты, повторное применение, сохранность данных и отказ при неверной контрольной сумме.

Дополнительно сохраняются проверки финансов перевозчика/заказчика, проекции менеджеров, маршрутов и интерфейса, а также обязательный CRITICAL preflight и CI.

## Реестр — согласованный контракт 2026-09-16

- 12 колонок: ID, описание, начало, окончание, статус, подрядчик/водитель, количество заявок, суммарный вес, менеджер, продажа, себестоимость, доходность.
- ID/описание/статус не переносятся; длинное описание сокращается с полной подсказкой и полным текстом в карточке. Узкое окно прокручивает только таблицу.
- Даты как в линейном реестре: факт приоритетен, иначе серый план с подписью; отсутствие обозначается прочерком. Открытые/полные диапазоны источника сохраняются. Отдельной красной подсветки просрочки нет, как и в текущем линейном реестре.
- Четыре выбираемых статуса: планируемый (системный фиолетовый), сформированный (бирюзовый), вывоз начался (зелёный), груз сдан (серый). Цвет занимает ячейку. Исторический searching_executor отображается/фильтруется как planned_route без backfill; cancelled остаётся внутренним историческим состоянием отмены/удаления и не предлагается в форме.
- Исполнитель: подрядчик, фамилия с инициалами водителя, машина отдельными строками. Пустой driver_id источника — прочерк без предупреждения. Указанный, но несопоставленный исполнитель — системная жёлтая ячейка «не нашлось соответствия с новой базой»; отдельные предупреждения утилизатора не подсвечивают исполнителя.
- Количество/вес берутся по всему составу рейса, включая поиск по одной заявке. Менеджер: имя и первая буква фамилии.
- Продажа/себестоимость повторяют финансовое отображение линейных рейсов: итог и строки условий, прочерк при отсутствии. Доступ к финансам остаётся только в finance realm. Доходность = (продажа − себестоимость) / продажа × 100 %, с одним десятичным знаком, включая отрицательные значения. Нет одной из сумм или продажа нулевая — прочерк; явно указанная нулевая себестоимость допустима. Это отображение договорной маржи, не факт оплаты и не пересчёт обязательств.
- Изменение не требует новой миграции или массового изменения данных.
