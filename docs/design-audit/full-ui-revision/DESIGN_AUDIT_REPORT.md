## Актуализация 2026-06-26 — Исполнители рейса / Транспорт

Статус: подготовлен пакет исправлений `ERP_ROUTE_EXECUTORS_VEHICLE_SETS_FIXED_STRUCTURE_v4_SCHEMA_REAL.zip`; перед финальной фиксацией владелец должен применить файлы, проверить runtime и затем закоммитить результат.

Что обязательно учитывать дальше:

- `/company/route-executors` должен быть доступен `company_owner`, `senior_logist`, `logist`. Для `logist` пустой список — это не «Нет доступа», а нормальное пустое состояние с действием `Создать исполнителя рейса`.
- `Исполнитель рейса` — пользовательская сущность `Подрядчик + водитель + ТС`; технически создаются/используются `driver_vehicle_blocks` + `crews`.
- Реальная локальная схема БД: таблицы сущностей находятся в `erp_company_{id}`, а не в центральной `erp_planex`.
- `driver_vehicle_blocks` НЕ имеет поля `vehicle_id`. Запрещено писать `vehicle_id` в `driver_vehicle_blocks`.
- `driver_vehicle_blocks` хранит: `driver_id`, `vehicle_set_id`, `status`, `comments`, `created_by_user_id`, `created_by_role`, `updated_by_user_id`, `updated_by_role`.
- `crews` всё ещё имеет legacy-поля `vehicle_id` и `driver_id`; при создании исполнителя рейса `crews.vehicle_id` нужно заполнять значением `vehicle_sets.primary_vehicle_unit_id`, а `crews.driver_id` — выбранным водителем.
- Для `logist` выбор contractor/driver/vehicle_set и видимость списков должны фильтроваться по `created_by_user_id` + активным grants. Активный grant: `revoked_at IS NULL` и `access_level IN ('view','edit')`.
- На `/company/vehicle-sets` модалка создания транспорта должна быть в DOM всегда, включая пустой список, иначе кнопка `Добавить новый транспорт` визуально есть, но не работает.
- Если возникает ошибка схемы БД, сначала запускать `db_schema_route_executor.php` и сверять реальные `DESCRIBE/SHOW CREATE TABLE`, не угадывать поля.

## 1. Общий вердикт

### Что сейчас с интерфейсом

ERP PLANEX — работающая система с полным функциональным набором: справочники, гранты доступа, каскадная видимость сущностей, документы, роли. Бизнес-логика реализована правильно. Однако **интерфейс не воспринимается как продукт** — он воспринимается как технический каркас, который ещё не прошёл продуктовый дизайн.

Система выглядит как набор отдельных страниц с одинаковым CSS, а не как единый рабочий инструмент для логистической компании.

### Почему система пока не воспринимается как цельный продукт

Четыре системных причины:

1. **Техническая информация не скрыта от пользователей.** В списках видны внутренние ID (`ID 1`, `ID БЛОКА: 1`), в карточках — `erp_company_9`, `storage/companies/9/`, в ошибках — `vehicle_unit`, `driver_vehicle_block`, `crew`. Пользователь видит бэкенд.

2. **Английские технические термины в русском интерфейсе.** Тип комплекта — `coupling`, уровень доступа — `edit`/`view`, статус компании при удалении — `active`. Перевод не завершён.

3. **Дашборды пусты.** Dashboard компании (owner и logist) — это просто список разделов, дублирующий сайдбар. Никаких счётчиков, никакого контекста, никакой ценности. Пользователь не понимает, что делать после входа.

4. **Иерархия данных в карточках отсутствует.** Все блоки выглядят одинаково: ОСНОВНЫЕ ДАННЫЕ — ПАСПОРТ — ВОДИТЕЛЬСКОЕ УДОСТОВЕРЕНИЕ — СНИЛС — ТЕЛЕФОНЫ — ... Нет главного блока, нет второстепенного, нет опасной зоны. Это не карточка сущности — это список полей.

### Главные UX-проблемы

- Пользователь не понимает, где он находится в системе и к какому разделу относится страница.
- После входа нет ни одного ориентира — что делать первым делом.
- На карточках нет главного действия (выделенного визуально).
- Опасные действия (Архивировать, Удалить) не отделены от навигационных кнопок.
- Страница документов при прямом открытии показывает техническую ошибку пользователю.
- Чувствительные персональные данные (паспорт, СНИЛС) вынесены в список водителей.

### Главные UI-проблемы

- Английские технические термины: `coupling`, `edit`, `view`, `active`, `ID X`.
- Пустые поля показываются как `—` даже для важных атрибутов (Тип единицы: `—`).
- Inconsistency в названиях блоков: «Доступ логистов» vs «Доступ пользователей» на разных карточках.
- Кнопки действий в таблицах (Просмотр / Редактировать / Документы) визуально не иерархичны.
- Заголовки карточек бессодержательны: `Блок #1`, `Комплект #1`, `Экипаж #1`.
- Всегда видимый disabled-пункт «Рейсы» в сайдбаре создаёт ощущение незаконченности.

## 2. Карта проблем по ролям

### SUPERADMIN

Интерфейс в целом адекватен роли мониторинга. Главные проблемы:
- Дашборд почти пустой: системная информация технического характера (`Среда: local`, `Статус БД: не проверялся`), блок «В разработке».
- В реестре компаний виден технический тест-объект `COMPANY_EDITED_VIA_RUNTIME` — имя без маскировки.
- Страница доступов компании: уровень доступа отображается как `edit` (английский), «Кем выдан» — пустое (`—`).
- На странице удаления компании показываются внутренние пути: `storage/companies/9/`, `erp_company_9`, статус — `active` (не «Активна»).
- Нет навигационных табов на карточке компании в хлебных крошках — контекст перехода понятен только если видишь topbar-crumbs.

### Руководитель компании (COMPANY_OWNER)

Наибольшая нагрузка. Главные проблемы:
- Дашборд бесполезен — дублирует сайдбар.
- В списке водителей видны паспортные данные и СНИЛС.
- Во всех списках — технические ID в подтексте строк.
- В карточке водителя СНИЛС выделен в отдельный блок ради одного поля.
- В карточке ТЕ поле «Тип единицы» пустое (`—`), хотя тип — критический атрибут.
- В карточке тягача блок называется «ДОСТУП ПОЛЬЗОВАТЕЛЕЙ», в карточке водителя — «ДОСТУП ЛОГИСТОВ» (несогласованность).
- Кнопка «Архивировать» и кнопка «Документы» стоят рядом без визуального разделения.
- Документы: прямой переход на `/company/documents` без параметров выдаёт техническую ошибку.

### Логист (владелец записей)

В целом видит то же, что owner, без блоков грантов. Проблемы:
- На карточках сущностей после удаления блока грантов (которого нет у логиста) остаётся визуальная пустота — структура карточки нарушена.
- Дашборд так же бесполезен.
- Видит disabled «Рейсы» и disabled «Настройки» в меню — оба пункта занимают место и создают ощущение недоделанности.
- Колонка «Создал» в списках показывает ему его же собственные записи, помечая их «Логист #1» — безличная метка.

### Логист с grant-доступом

Самый уязвимый пользователь с точки зрения UI. Проблемы:
- Большинство списков для него пустые (нет своих записей, нет грантов) — нет нормального empty state с объяснением «Чтобы видеть записи здесь, Руководитель должен выдать вам доступ».
- На карточке экипажа (через грант) виден блок «ТЕХНИЧЕСКАЯ ИНФОРМАЦИЯ» (даты создания/обновления) — эту информацию логисту не нужно видеть.
- **Критически**: при наличии гранта `edit` на уже заархивированный экипаж кнопка «Архивировать» всё равно показывается. Логист может нажать «Архивировать» на уже архивном объекте.
- Кнопка «Редактировать» видна в заголовке карточки экипажа в режиме grant-доступа с уровнем edit — это корректно, но визуально не ясно, что именно логист может редактировать.

## 3. Карта проблем по меню

### SUPERADMIN — Компании

Структура: СИСТЕМА → Компании + disabled Настройки.  
Проблемы: «Настройки» disabled — занимает место, вводит в заблуждение. Глубокая навигация по разделам компании (Обзор / Руководитель / Пользователи / Справочники / Документы) реализована через горизонтальные табы на карточке компании — правильное решение, но активный таб не всегда явен.

### Пользователи (company_owner)

Пункт «Пользователи» находится в группе «СИСТЕМА», что разумно. Проблема: в сайдбаре owner нет визуального разделителя между «Рейсы» (disabled) и остальными рабочими пунктами. Disabled «Рейсы» стоит первым в списке операций.

### Подрядчики

Пункт назван правильно. В списке: колонка «СОЗДАЛ» занимает место, которого при малом числе колонок не хватает. При большом числе колонок (ПОДРЯДЧИК + РЕКВИЗИТЫ + КОНТАКТ + СОЗДАЛ + СТАТУС + действия) таблица перегружена.

### Водители

Пункт назван правильно. В списке водителей колонка «ДОКУМЕНТЫ» показывает номер ВУ, паспорт и СНИЛС — личные данные не должны быть в списке.

### Транспортные единицы

Раздел правильно называется «Транспортные единицы» в меню (не «Транспорт»). В таблице колонка «ПАРАМЕТРЫ» показывает значения типа `— / Грузоподъёмность` — метка без значения выглядит как баг.

### Транспортные комплекты

Правильно. В таблице тип отображается как `coupling` (английский) — критичная проблема перевода.

### Водитель+ТС

Заголовок раздела `Блоки "Водитель + ТС"` с кавычками выглядит технически. В меню отображается как «Водитель+ТС» без пробелов — мелкое оформление. В карточке — название `Блок #1` нечитаемо.

### Экипажи

Лучший список в системе (видны подрядчик, водитель, транспорт, статус). Проблема: тип комплекта — `coupling`.

### Документы

Раздела «Документы» нет в сайдбаре — переход только из карточек сущностей. При прямом переходе без параметров выдаётся техническая ошибка. Пользователь не понимает как попасть к документам не через карточку.

### Доступы (гранты)

На карточках сущностей: блок называется «ДОСТУП ЛОГИСТОВ» на водителе и экипаже, «ДОСТУП ПОЛЬЗОВАТЕЛЕЙ» на ТЕ. Нужно единое название.

## 6. Рекомендованные правила карточек

Единый шаблон для всех view-карточек:

**Зона 1 — Идентификация (page-head)**  
Всегда первая. Содержит: название/идентификатор сущности (не «Блок #1», а «Петров + A111AA777»), статус-бейдж, кнопки главных действий (Редактировать — primary, Документы — secondary, ← К списку — ghost).

**Зона 2 — Ключевые данные (panel сверху)**  
Самые важные поля: для водителя — ФИО + телефоны + статус. Для подрядчика — название + ИНН + тип + контакт. Для ТЕ — госномер + тип + марка/модель + статус.

**Зона 3 — Связанные сущности**

## 7. Рекомендованные правила таблиц

**Максимум колонок для списка:** 4–5 видимых + колонка действий.

**Что объединять:**
- Название + идентификатор + тип → в одну колонку с двумя строками (main + sub).
- ИНН → перенести sub-строкой под названием компании/подрядчика.
- Телефон → sub-строкой под ФИО.

**Что убирать из таблиц:**
- Технические ID (`ID 1`, `ID БЛОКА`).
- Персональные данные (паспорт, СНИЛС).
- Технические статусы на английском.
- Колонку «Создал» у owner можно оставить, но сделать последней и показывать реальное имя пользователя, не «Логист #1».

**Действия в таблице:**
- Просмотр (главное действие — сделать кликабельной строку или дать чёткую кнопку)
- Редактировать
- Документы
- Кнопки располагать справа в фиксированной колонке (`.col-actions`).
- Опасные действия (Архивировать) — не в таблице, только в карточке.

**Пустые состояния:**
- Показывать `.empty-state` с заголовком «Нет [подрядчиков / водителей / …]» и кнопкой создания.
- Для логиста с грант-доступом (LOGIST 2): добавить объяснение «Записи появятся здесь, когда Руководитель выдаст вам доступ».

**Типы в таблицах:**
- Все технические enum-значения переводить: `coupling` → «Сцепка», `single` → «Одиночное ТС», `road_train` → «Автопоезд».

## 8. Рекомендованные правила форм

**Группировка полей:**
- Обязательные поля — в верхней секции (ОСНОВНОЕ).
- Рекомендуемые поля — в средней секции (ДОПОЛНИТЕЛЬНО), с пометкой «рекомендуется» или без звёздочки.
- Технические поля (комментарий, статус) — в нижней секции.

**Маркировка:**
- Обязательные поля: `*` (звёздочка) + пояснение «* Обязательное поле» под заголовком формы.
- Необязательные поля: подпись «необязательно» серым текстом рядом с меткой (не через * absence, а явно).

**Ширина полей:**
- Короткие поля (ИНН, КПП, ОГРН, телефон): показывать в строку, не растягивать на всю ширину.
- Длинные поля (адрес, комментарий): textarea.
- ФИО: полная ширина.

**Пустые dropdown без данных:**
- Select показывает «— Нет доступных [водителей] —» + ссылку «Создать водителя» под полем.

**Кнопки:**
- «Создать / Сохранить» — `.btn-primary`.
- «Отмена / ← К списку» — `.btn-ghost`.
- Размещение: слева направо (primary → ghost).
- Кнопку «Отмена» не терять (сейчас в форме водителя кнопки «Отмена» нет).

**Ошибки:**
- Показывать под конкретным полем, не только вверху формы.
- Текст ошибки: конкретный, без технических деталей.
