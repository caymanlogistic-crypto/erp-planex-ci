# Продолжение работы с каноном PLANEX

## Новый чат проекта

«Приведи к каноническому виду страницы: …» означает адаптацию перечисленных страниц с сохранением данных, прав и действий, проверки и обычный выпуск ERP. «Пока песочница» останавливает выпуск до явного «ВНЕДРЯЙ» с выбранной версией.

«Ты дизайнер системы, продолжаем работу» означает прочитать этот документ, канон, каталог и решения, открыть цельную витрину и продолжать с несогласованных ролей. Уже утверждённые элементы заново не проектировать. Предлагать по 3–5 связанных состояний.

## Источники

Последнее решение OWNER → `decisions-20261018.json` → точный `REGISTRY_CANON.md` → общие CSS/JS/partial → каталог и генерируемая витрина. Галерея не утверждает сама себя. Подключение старой оболочки не означает завершённую адаптацию: четыре исходных экрана имеют статус `legacy_shared_shell_pending_20261018` до отдельного проверенного переноса.

## Адаптация

1. Составить карту «элемент страницы → роль каталога», отдельно выписать пробелы и бизнес-сценарии. Прочитать только относящиеся к задаче память и код.
2. Использовать общий partial шапки, CSS и JS. Таблица `registry-ui-data`; данные: `registry-ui-primary`, `registry-ui-name`, `registry-ui-secondary`, `registry-ui-money`, `registry-ui-missing`, `registry-ui-id`, `registry-ui-trip-cell`/`registry-ui-trip`. Удалить локальные перекрытия. Одних классов недостаточно — проверить computed styles.
3. Native controls: `data-registry-field`, явный `data-registry-default`. Корень: `data-registry-id`, **серверный** `data-registry-state-scope` с account, membership/ролью, компанией и ревизией прав. Недоступные controls не рендерить на сервере. Хранилище не даёт прав. Сброс `.registry-ui-reset` сразу после поиска внутри `.registry-ui-search-group`.
4. `PlanexRegistry.mount(root)` вызывать после предметных обработчиков. Вкладки: `data-registry-tab`, начальная — `data-registry-default-tab`. Общий API вызывает обычные input/change/click; расчёты, отбор и сортировка остаются предметными. После обновления данных — `PlanexRegistry.textRoles(root)`. Полный текст для поиска — `data-registry-full-text`, не сокращённый span.
5. Прокрутка: `registry-ui-sticky-table registry-ui-scroll`; обёртка `.table-scroll`/`.rp-v010-table-wrap` без своего вертикального ограничения. Один настоящий thead. Запрещены копии JS измерения и локальные top/max-height.
6. Сохранить все поля и адаптивные режимы страницы, включая 13 финансовых колонок, двухполосный режим и карточки. Базовые карточки данных требуют `data-label` на ячейках и единую обёртку значения `.registry-ui-value`; номер/дата, имя/пояснение остаются одним вертикальным блоком. Не заменять страницу демонстрационными данными витрины.
7. Регистрировать адаптированную страницу со статусом `current_20261018` и реальным браузерным контрактом. Каталог, guard, браузер, затем при принятом Design Lab checkpoint — localhost parity на одинаковых fixtures. Принятие checkpoint только по разрешению OWNER.
8. Обычный ERP выпуск: focused tests → final local publisher → PR/CI → merge → MEMORY → deploy при изменении runtime. Согласование дизайна само по себе не разрешает публикацию.

## Проверки результата

390/1280/1920/3840 CSS px; реальные IBM 400/500/600/700; normal/hover/focus/open/selected; длинные и пустые данные; ID `#0000` и длиннее; 30 графем и поиск по полному значению; ноль результатов; деньги/итоги; один вертикальный scroll; совмещение thead/строк при горизонтальном scroll; сброс каждого фильтра/вкладки/checkbox; перезагрузка; битое/устаревшее хранилище; смена пользователя/роли/компании; недоступный localStorage. Права и расчёты не менять ради сходства.

## Новое решение

Предложение → песочница → явное решение OWNER → общий компонент → точный контракт и браузерный тест → каталог → `ui_standard.py render` → обычный выпуск. Принятое значение меняется только новым решением. Предложенные/отклонённые варианты не являются APPROVED.

## Ещё не согласовано

- Формы, подтверждение удаления, загрузка/удаление файлов, серверные ошибки и ожидание.
- Универсальное устройство/типографика меню действий: согласованы цвета удаления, но не все меню и диалоги.
- Последний визуальный вариант фильтров компании/квартала руководителя. Запрос и начальные значения записаны; отдельного подтверждения конкретной версии ещё нет. При будущем переносе проверять `isSystemOwner()`, не расширенный доступ менеджеров.

Это отдельная очередь, не препятствие использованию утверждённых ролей реестров.
