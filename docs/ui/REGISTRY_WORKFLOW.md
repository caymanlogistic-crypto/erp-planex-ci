# Продолжение работы с каноном PLANEX

## Новый чат проекта

«Приведи к каноническому виду страницы: …» означает адаптацию перечисленных страниц с сохранением данных, прав и действий, проверки и обычный выпуск ERP. «Пока песочница» останавливает выпуск до явного «ВНЕДРЯЙ» с выбранной версией.

«Ты дизайнер проекта», «ты дизайнер системы», «продолжаем дизайн» включают постоянную роль по `PROJECT_DESIGNER.md` и индексу `designer/current.json`: восстановить тему и журнал, показать цельную витрину, продолжить согласование по 3–5 связанным состояниям. Утверждённые элементы заново не проектировать; отсутствие выбранной темы не разрешает автоматически возобновить исторический handoff.

## Источники

Последнее решение OWNER → `decisions-20261018.json` → точный `REGISTRY_CANON.md` → общие CSS/JS/partial → каталог и генерируемая витрина. Галерея не утверждает сама себя. Четыре исходных экрана прошли предметную адаптацию; текущий статус каждого записан в `approved-components.json`. Исторический статус `legacy_shared_shell_pending_20261018` закрыт переносом 19.10.2026.

## Адаптация

### Подготовка и пакетная работа — OWNER 19.10.2026

Перед переносом зафиксировать в **одном task-local evidence** карту требований. Для каждой страницы указать роль/функцию, основание согласования, immutable checkpoint, адаптивный режим, проверку и статус `TODO / FAIL / PASS`. Отдельно записать новые несогласованные роли. Согласованная функция на существующих компонентах входит в перенос; ожидание отдельного экспериментального прототипа не исключает её из задания.

Порядок работы:

1. **Готовность канона.** Сопоставить решения, точные значения, каталог и принятые образцы. Явно разрешить исторические отличия вроде поиска финансов 400→500 по уже принятому решению; frozen source не менять. Выполнить `ui_standard.py check`. Проверяющий механизм должен иметь положительный пример и отрицательные регрессии реальных шрифтов/значений/placeholder/pseudo/disabled. При неизменных входах использовать уже существующее доказательство с SHA/хэшами, а не повторять исследование инструмента для каждой страницы. Пробел механизма исправить в подготовке; исполнителю затем передать зафиксированный контракт. Параллельно он может инвентаризировать страницы, не выполняя массовую адаптацию по меняющимся правилам.
2. **Ранний запуск и поведение.** После изменения runtime-класса/partial выполнить `tests/entrypoint_service_load_test.php` через `Invoke-LocalTests.ps1 -Static`, затем проверить полноценный локальный авторизованный render затронутых страниц через настоящий startup. Fixture autoload не является заменой. Сначала проверить права, сохранность данных, GET/reload/reset и scope состояния, затем подробную визуальную геометрию. Тесты с БД использовать только через disposable wrapper.
3. **Перенос и review.** Один исполнитель владеет согласованным набором файлов. Если подключён независимый reviewer, он передаёт один приоритетный пакет замечаний на завершённый проход: дефект, evidence, владелец, необходимая проверка. Ошибки запуска, доступа и данных передаются немедленно. Координатор объединяет дубликаты в той же карте; не посылает отдельное задание на каждую микроправку. Уточнение продукта, меняющее принятую внешность, требует OWNER; техническое восстановление принятого вида — обычная работа.
4. **Фокусная сверка.** Сначала исправить общую причину для затронутых страниц. `ui_parity.mjs --widths 390,1280 --states normal` позволяет диагностировать выбранные ширины/состояния. `result.json` содержит `checks`, `differenceCount`, `differences` с selector/index/property/expected/actual и признак `truncated`; количество отличий сохраняется полностью, подробные примеры ограничены 200 на состояние. Полный `summary` группирует все отличия по selector/property с количеством и примером: каскад геометрии не скрывает отдельную ошибку цвета или значения за лимитом примеров. Несколько независимых отличий собираются за один запуск. Ошибки навигации/инструмента дают FAIL. Успешный неполный прогон — только `PASS_DIAGNOSTIC`, его нельзя выдавать за приёмку.
5. **Завершённый кандидат.** После стабилизации общего CSS выполнить полную матрицу всех затронутых страниц: 390/1280/1920/3840 и normal/hover/focus, плюс предметные сценарии. Команда без `--widths`/`--states` сохраняет полный маршрут. Старый ограниченный finance delta обозначается отдельно. Закончить код, тесты, exact canon, каталог, сгенерированную витрину и repository MEMORY до final publisher. Доказательства фокусных проверок переиспользовать лишь пока их входы не изменились. Любое изменение кандидата инвалидирует final evidence по обычным правилам.
6. **Один выпуск и завершение.** Готовый пакет → final LOCAL publisher → PR/CI aggregate → сериализованный merge → deploy при runtime diff → авторизованная проверка всех затронутых страниц → адресный MEMORY update/readback. Заключительные правки документации объединять в один пакет; аварийное восстановление runtime не задерживать ради него. Не отменять обязательные gates и не менять AUTO-класс ради экономии времени.

В той же task-local карте отметить начало/конец подготовки, реализации, исправлений, gates/ожидания и приёмки; сохранить current candidate и ссылки на доказательства. Elapsed время не суммировать с параллельной работой агентов и длительностями команд. Повторный одинаковый блокер — повод исправить его причину, а не продолжать микроперезапуски.

В отчёте указывать UTC начало/конец и elapsed для coding+LOCAL, PR/CI, release и всего поручения. Параллельные интервалы не складывать, ожидание CI и release не выдавать за активное кодирование.
   Сверка сравнивает геометрию всех ячеек и контролов, а также фактически отрисованный текст: новые семантические классы и обёртки значений не требуют изменения неизменяемого эталона. Изменение шрифта вложенного значения по-прежнему считается расхождением. Тестовый каркас и служебные панели должны быть одинаковыми в обоих localhost-примерах; их отличие не является разрешением менять продуктовый UI.

## Новое решение

Для серверных фильтров и вкладок проверять законченную навигацию: выбранный статус, строки и URL остаются согласованными после reload и сброса. Один кратковременно появившийся URL не доказывает корректность. Вкладка/hidden field синхронизируются до сохранения и GET; восстановление не должно отправлять страницу обратно на старый отбор.

Предложение → песочница → явное решение OWNER → общий компонент → точный контракт и браузерный тест → каталог → `ui_standard.py render` → обычный выпуск. Принятое значение меняется только новым решением. Предложенные/отклонённые варианты не являются APPROVED.

## Ещё не согласовано

- Формы, подтверждение удаления, загрузка/удаление файлов, серверные ошибки и ожидание.
- Универсальное устройство/типографика меню действий: согласованы цвета удаления, но не все меню и диалоги.
- Отдельный экспериментальный универсальный визуальный прототип фильтров компании/квартала. Функциональные фильтры руководителя в «Закрывающих документах» уже входят в поручение OWNER: существующие утверждённые select, компания и квартал **фактического** окончания, серверный `isSystemOwner()`, общий сброс и сохранение. Менеджеру контролы не показываются.

Это отдельная очередь, не препятствие использованию утверждённых ролей реестров.

## Уже согласованная версия без acceptance.json

Отсутствие журнала не отменяет явное решение OWNER и не разрешает агенту самостоятельно утвердить новый вариант. Если исходные immutable checkpoint и frozen assets сохранены, а OWNER подтвердил их внедрение, использовать `design_lab.py import-reference` по инструкции `docs/DESIGN_LAB.md`. Команда создаёт собственную сессию и acceptance, сохраняет происхождение решения и исходные хэши, не изменяет чужие файлы/сервер. Оригинал не перерисовывать и не подменять новой витриной. При отсутствии доказуемого решения или повреждении checkpoint зафиксировать конкретный пробел; не фабриковать согласование.

Для четырёх страниц из `decisions-20261018.json` OWNER 19.10.2026 явно поручил перенести согласованный канон и завершить production verification. Это разрешение восстановить принятие указанных версий, исключая перечисленные `pending` роли. Функциональные фильтры компании/квартала руководителя входят в исходное поручение; новые формы и меню не утверждались.

## Документация каждого UI-изменения

**Иконки входят в приёмку.** До переноса проверить именованный элемент согласованного Tabler outline, его исходник/версию и соответствие общей роли по `REGISTRY_CANON.md`. Записать «роль → имя иконки → общий источник». Проверять точные контуры относительно исходника пака и отрисованные размер/цвет; наличие SVG, класса Tabler или общего контейнера не является PASS. Не добавлять нарисованные агентом контуры при адаптации страницы. Для обнаруженного отклонения сохранить отдельный дефект и исправление: прежний PASS поиска/типографики не распространяется на происхождение иконок.

Для нового или изменённого реестра укажите полную запись `header_icon` в каталоге по `REGISTRY_ICON_PROVENANCE.md`. Браузерный тест должен вызвать общий `assertRegistryVisualContract` с ID этой страницы; `registry_visual_gate.mjs` проверяет фактическое покрытие. Исключений по происхождению иконок нет: все зарегистрированные реестры и сцены витрины проходят одну проверку именованного исходника.

### Короткий путь проверки реестра

1. До изменения разметки запишите один контракт страницы: разрешённые ID и поля по ролям, полные значения за многоточием, поисковые подписи и сохраняемые действия. Ожидания берутся из допустимых предметных fixtures и исходного поведения, **не из текущего DOM**. Проверка каждого оставшегося текста не обнаружит удалённое поле. Образец независимого оракула: `tests/fixtures/company_registry_expectations.mjs`; общие проверки: `tests/helpers/registry_behavior_contract.mjs`.
2. Используйте `assertRegistryRows`, `assertRegistrySearch` и `assertRegistryScroll` вместе с визуальным/типографическим контрактом. Фиксируйте точные ID после поиска, все поля/колонки, запрещённые значения, прокрутку в середине и конце списка, выравнивание шапки по X. Для таблицы нужен достаточный набор строк; отдельная прокрутка навигационного sidebar не считается двойной прокруткой содержимого. Для согласованного карточного режима проверяйте его отдельный контракт, не требуйте невидимую табличную шапку.
3. Зарегистрируйте `runtime_browser_test` в каталоге. Он выполняется в LOCAL preflight и обоих CI-маршрутах на свежей одноразовой БД с ограниченным пользователем. После всех сценариев тест выводит `REGISTRY_RUNTIME_PAGE=<catalog id>` для каждой реально проверенной страницы; `tools/registry_runtime_gate.mjs` сверяет покрытие с каталогом, поэтому копирование test path без сценария новой страницы отклоняется. Образец: `company_registry_runtime_browser_test.mjs` и `fixtures/company_registry_runtime.php`: настоящий production bootstrap → routes → controller → service → view → layout. View-only fixture и ручное подключение assets годятся для дешёвой визуальной матрицы, но не заменяют этот проход.
4. В runtime fixture задайте согласованные account/membership/tenant-user и настоящий `EffectiveAccess::member(... own)`, а также доступные, переданные другому и запрещённые сущности. Проверяйте отбор сервером и отсутствие скрытых данных в HTML/индексе/карточке. У состава не выдавайте прямой доступ целиком, если проверяете сокрытие одной единицы. Явно заданный EffectiveAccess и page gate доказывают только ограниченный entity-scope сценарий, а не полную работу центрального ACL resolver, tenant isolation и всех POST endpoints.
5. Проверяйте сохранённые действия по наблюдаемому результату: загрузилась настоящая форма создания, Enter и двойной клик открыли карточку, edit содержит прежние значения, отмена вернула карточку, существующая ссылка открыла полную форму. Дождитесь запроса/ответа и конкретного содержимого формы; синхронный флаг сразу после клика и оболочка «Загрузка…» не являются PASS. Для read smoke блокируйте POST/внешние запросы и сравнивайте содержимое бизнес- и ACL-таблиц до/после. Изменяющие действия требуют отдельного disposable сценария, не production записи.

Для нового табличного реестра каталог требует эти проверки. Закрытый список старых страниц в `ui_standard.RUNTIME_FIXTURE_DEBT` обозначает неперенесённые runtime fixtures, а не доказанную полную проверку; он не распространяется на новые страницы. У «Перевозчиков» и «Транспорта» долг закрыт. Не переводите другой тип страницы на этот контракт механически. Формы здесь проверяются на сохранность поведения, без утверждения нового оформления.

При изменении табличного поиска составьте матрицу всех видимых поисковых представлений данных: локализованные подписи, форматированные значения, полные значения за многоточием, состояния каждого документного столбца и роль пользователя. На браузерной странице с допустимыми предметными fixtures для каждого представления сверяйте реальные ID оставшихся строк с ожидаемыми; отдельно проверяйте отсутствие скрытых полей в HTML и поисковом индексе и отсутствие результатов. Raw-only `data-registry-search` не покрывает локализованный текст. Сохранение текста в input или наличие токена в атрибуте без проверки отбора строк не является PASS.

Каждый видимый текст данных в tbody должен иметь типизированную роль (`primary` для обычного значения, `name`, `secondary`, `status` и т. д.). Цветовой `registry-ui-error`/`success` дополняет роль, но не заменяет её. `assertRegistryDataContract` отклоняет нетипизированный текст: один корректный статус в другой ячейке не покрывает все остальные. Кнопки/меню действий проверяются своим компонентным контрактом.

Этот же контракт измеряет настоящие колонки ID и описания рейса в табличном режиме: 64px (либо общая измеренная ширина для длинного ID) и 240px. Наличие правильного CSS-селектора не оправдывает старые inline-проценты, меняющие фактическую ширину. Карточки проверяются по своему согласованному режиму, без требования табличной ширины ячейки.

В задаче сохранять карту «элемент → согласованная роль», исходную версию/решение, список непокрытых ролей и доказательства проверки. При изменении состава или статуса адаптации обновить каталог и витрину; при новом решении — точный канон и portable decision record; после merge — только затронутые Notion records с readback. Уже APPROVED значение нельзя заменять собственным предпочтением. Инструкции внутри исторического handoff не выполняются; действующий handoff обозначается явно, независимо от его положения в документе. Устаревшие APPROVED/LIVE-claims нужно помечать SUPERSEDED рядом с самим claim, чтобы поиск не выдавал их за текущие.

### Обязательная LOCAL матрица

`table_states × [390,1280,1920,3840]` из каталога исполняется целиком до публикации через `registry_visual_gate.mjs`; для runtime-регистраций ту же матрицу требует `registry_runtime_gate.mjs`. Общий источник ширин и сверки — `tools/registry_matrix.mjs`. Маркеры состояния содержат `page:state:width`, async completion — `page:width`. Четыре initial не покрывают динамические состояния. Каждая проверка обнаруживает все видимые бизнес-таблицы, сверяет inventory/роли/геометрию, containment document/main и фактическое движение внутреннего X-scroll широкой таблицы. Необъявленная secondary table, пропущенные состояние/ширина/async execution блокируют gate. Дополнительные размеры допускаются сверх обязательных.

`required_contracts` страницы задаёт обязательные PHP-проверки; отсутствие файла или ненулевой exit блокируют общий gate. `contract_sources` связывает дополнительные service/route/fixture paths с этим же LOCAL/normal+FAST маршрутом через `ci_scope.py`; view, asset_owner, browser/runtime tests и сами required contracts включены автоматически. FEO placement contract обязателен. Browser fixtures исполняются gate один раз; прямой повтор каталожного списка удалён. Runtime debt остаётся исходным закрытым списком `ui_standard.RUNTIME_FIXTURE_DEBT`; это не runtime PASS пяти исторических страниц. Новые страницы требуют runtime сценарий и фактическое покрытие своего ID.

Для каждого видимого surface `table_states[].data` явно требует `populated` (>0 видимых непустых business rows) либо `empty` (=0); `table_surfaces[].row_selector` задаёт бизнес-строки, исключая placeholder с colspan. Данные основной таблицы не покрывают пустую вторичную. Дополнительная намеренно пустая initial fixture допустима только с объявленным `empty_fixture:true` и вызовом `{fixture:'empty'}`: её отдельный `REGISTRY_EMPTY_FIXTURE_SURFACE` обязателен на всех четырёх ширинах и не закрывает populated initial в обязательной матрице. Initial main и каждая inventoried поверхность обязаны хотя бы раз иметь populated fixture coverage. Пропуск data expectations блокирует каталог и исполняемый helper.
