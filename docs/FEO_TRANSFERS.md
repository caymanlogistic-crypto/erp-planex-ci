# Перенос заявок ФЭО

Владелец уточнил требования 18.09.2026: новая ERP меняет только адрес МНО и две координаты; операции и возврат выполняются целым пакетом; неизвестные заявки блокируют запись; точность Яндекса информирует пользователя и входит в MAX-сообщение, но сама по себе не блокирует перенос.

## Страницы и доступ

- `/company/feo/requests/transfers`, `company.feo.transfers`: история, проверка, создание, возврат, просмотр и выгрузка пакета.
- `/company/feo/requests/coordinates`, `company.feo.coordinates`: самостоятельный геокодер.
- Обе страницы grantable в PageRegistry. Роли и персональные allow/deny действуют на меню и все прямые HTTP endpoints. Новые права по умолчанию доступны руководителю; остальным выдаются явно.
- Общий POST геокодирования разрешён при доступе к любой из двух страниц. Сохранение API-ключа требует системного руководителя и защищено owner-only registry key.

## Данные и возврат

Миграция `139_create_feo_transfers.sql` создаёт только пять новых таблиц. Существующие поля клиентской базы не переименовываются и не переставляются. `mno_sh` хранит долготу, `mno_d` — широту; геокодер возвращает корректно названные `longitude`/`latitude`.

Создание, история, текущие overrides, MAX outbox и очередь будущего legacy transport сохраняются в одной транзакции под общим FEO advisory lock. Заявки назначения и источники повторно читаются с блокировкой; хеш серверного preview защищает от изменения адреса или цепочки переносов между проверкой и записью. Идемпотентность: уникальный хеш случайного серверного preview token. Preview связан с account/company и действует 30 минут.

Откат восстанавливает **весь пакет**. Для пересекающихся пакетов сначала возвращается более поздний. Проверяется фактический row ID, текущий пакет и точное совпадение трёх текущих полей с after snapshot; конфликт любой строки откатывает всю транзакцию. NULL исходных координат сохраняется. Другая бизнес-информация не откатывается.

Импорт, возврат импорта и восстановление импорта сохраняют три географических поля активных переносов, обновляя остальные поля штатно. Откат импорта, удаляющий перенесённую заявку, блокируется до возврата её пакета. Ручное редактирование места активного переноса через старую карточку блокируется; остальные поля редактируются штатно.

## Геокодирование

`YandexGeocodingService` — переиспользуемый серверный модуль. Конфигурация: зашифрованный ключ компании в `geocoding_settings`, при отсутствии — серверная переменная `YANDEX_GEOCODER_API_KEY`. Секреты не находятся в Git и не возвращаются в HTML/JSON.

Результат сохраняет query, нормализованный адрес, настоящие широту/долготу, precision, kind, provider и время. Значения precision описаны в [документации Яндекса](https://yandex.ru/maps-api/docs/geocoder-api/response.html). Для существующей заявки без сохранённого результата геокодирования точность считается неподтверждённой. Неверные/отсутствующие координаты блокируются; корректные неточные координаты разрешены с предупреждением. Перетаскивания точки нет; точка открывается на Яндекс Картах.

## MAX

`feo.transfer.created` и `feo.transfer.reverted` используют существующие `MaxEventCatalog` / `MaxEventNotificationService`: чат, шаблон, формат, включение и повтор отправки на вкладке «События». Обязательная переменная `{{quality}}` не может быть убрана из шаблона. События по умолчанию отключены до выбора чата владельцем, как и существующее событие размещения. HTTP отправляется после commit; ошибка отправки не отменяет перенос и отображается менеджеру.

## Будущий обмен со старой базой

`feo_transfer_outbox` содержит неизменяемую операцию transfer/revert, before/after по каждой заявке и явное соответствие координат. Статус `awaiting_connector` означает **не отправлено**. JSON-выгрузка включает ID компании и операции в порядке их создания. Экспорт не помечает операцию доставленной.

Подключение к старой базе в этой версии отсутствует. После получения разрешённого API/схемы получателя адаптер должен обрабатывать очередь по ID, использовать company + outbox ID как ключ идемпотентности, сверять before перед записью, сохранять подтверждение и не перезаписывать внешние изменения молча. Код не открывает legacy-соединение и не пишет в `/erp`.

## Ввод в эксплуатацию

Публикация кода не запускает миграцию. До отдельного разрешённого применения 139 страницы показывают состояние ожидания обновления. Настройка ключа и события MAX производится через интерфейс руководителя. Production schema changes требуют отдельного task-specific OWNER разрешения; тестовые данные и сообщения на production не создаются этим изменением.
