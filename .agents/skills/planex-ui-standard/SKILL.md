# PLANEX UI standardization

Use when the OWNER says «стандартизируй страницу», asks to bring a page to agreed styles, or asks to extend agreed UI components. Follow the normal ERP task/worktree/publication rules in `AGENTS.md`.

OWNER 2026-10-18: reuse the currently approved components for every UI change. Do not introduce parallel presentation under another selector, inline style, custom property or JS style mutation. Run `python tools/ui_style_guard.py --base <START_HEAD>` during development; local preflight and both CI routes require its exact base/head result plus the catalog and browser contracts. Old presentation debt may be removed, not copied or extended. Only business column geometry belongs in page CSS. Missing roles require an explicit OWNER-approved extension of the shared source; a new catalog entry alone does not exempt a parallel stylesheet.

Read docs/ui/REGISTRY_WORKFLOW.md, docs/ui/REGISTRY_CANON.md, docs/ui/decisions-20261018.json and the later docs/ui/decisions-20261023-toolbar.json before building a new registry. The later decision fixes reset first on the right, search last, and the left checkbox group only on pages that already have one; finance, FEO placement and FEO transfers have different labels and defaults. Use the single complete gallery composition and switch its registered examples; do not restore repeated isolated previews. Inspect page adaptation_status: `current_20261018` is a stable catalog enum, not the date of the newest canon. Gallery CSS must never style preview descendants. For a localhost viewer use a task-owned Design Lab with preset `ui-standard`. New sessions freeze visual dependencies with SHA-256, checkpoints and acceptance. Before transferring a Design Lab checkpoint, compare the accepted sandbox and actual local implementation with identical fixtures using `node tools/ui_parity.mjs --reference-url <localhost> --candidate-url <localhost> --output <evidence>`, then exercise the remaining page-specific states. Preserve the same approved component appearance in the gallery, sandbox and ERP.

## Standardize a page

0. Complete the readiness phase in `docs/ui/REGISTRY_WORKFLOW.md` before changing pages: one requirement/evidence matrix, immutable references, exact responsive profiles and explicit known deltas. Verify catalog/checker readiness with existing evidence for unchanged inputs; repair missing coverage before mass adaptation. After changing runtime classes/partials, run `php tests/entrypoint_service_load_test.php` through the local static wrapper and verify full local page rendering without fixture-only autoload before detailed visual work. With a reviewer, collect one prioritized findings batch per pass, immediately escalating startup/access/data defects.

1. Open `docs/ui/approved-components.html` for visual discovery, run `python tools/ui_standard.py list`; inspect the applicable family with `show <id>` and read its `canon` file. For a tabular registry, use `registry` and `docs/ui/REGISTRY_CANON.md`. Do not force registry markup onto a different page type. If no approved family covers the page, reuse applicable approved components from `docs/ui/DESIGN_STANDARD.md` and Notion `09A — DESIGN SYSTEM — START HERE`, then record uncovered roles. A new visual pattern needs an explicit OWNER decision.
2. Inspect the actual page and its styles: identify every header, tab, toolbar, control, table/card and state, plus local CSS/JS selectors that currently own appearance or behavior. Map each shared role to a catalog component. Preserve business logic, data, accessibility and existing actions.
3. Use the canonical partial, classes, stylesheet and behavior source from the family. Remove or scope legacy local declarations that still override a shared role. A class name alone is not proof of reuse: inspect computed styles and geometry. Page CSS may contain only business column geometry; status calculation and unique actions stay in page behavior, while their presentation belongs to the shared owner.
   For registry toolbars, do not add visible prefix labels such as «Сортировка по:»; give every control an accessible name. Use `registry-ui-checkboxes` for groups: ordinary checkboxes are brown, and only `registry-ui-checkboxes--trip-status` may use semantic trip-status colors.
4. Register an adapted page with `python tools/ui_standard.py register page <definition.json>`; the definition needs `id`, `family`, `route`, `view`, a real `browser_test` path, explicit `sticky`/`reference_select` booleans, `adaptation_status:current_20261018` and applicable `data_roles` for a registry. The browser test calls `assertRegistryVisualContract` and `assertRegistryDataContract(page, 'catalog-page-id')`; use populated varied fixtures covering every declared role before empty/filter scenarios. Actual visible font family, nested typography/color and nonempty role coverage are mandatory. A class-name substring or loaded font file is not appearance evidence. Run `python tools/ui_standard.py check`; the registry contract reads the catalog automatically.
5. Run focused functional/browser tests through the local wrappers. At 390, 1280 and 1920 CSS px check the outer frame, toolbar-to-table contact (0 px gap), text/control dimensions, clipping and page overflow. Check 3840 px for bounded width. Exercise long/empty values, hover, focus, keyboard, sticky scroll and page-specific states. Compare with the current gallery and latest OWNER-approved reference; an older production implementation never overrides a newer canon decision. Add a browser regression for a discrepancy that escaped existing checks. Do not report completion from a green static contract alone.

During corrections, `ui_parity.mjs --widths 390,1280 --states normal` collects independent differences in one JSON report; `PASS_DIAGNOSTIC` is never final acceptance. The default command still checks all four widths and normal/hover/focus. Finish code, tests, catalog/gallery and exact documentation together before the final publisher. Follow the workflow stop criteria; do not open a new PR for every closing wording correction.

## Extend the standard

When an approved component does not cover a needed role, determine whether it is a variant of an existing family or a new family. Obtain an explicit OWNER decision for new visual values; a screenshot or existing local CSS alone does not grant approval. Put shared appearance in the family's canonical stylesheet and shared behavior in its canonical JS. Document exact values, states, responsive behavior, scope and approval in its `canon` file. Add a browser test that checks the rendered role, including existing family reference pages. Register the family/component with `python tools/ui_standard.py register family|component <definition.json>`, then run `check` and focused browser tests. `register` rejects an unapproved component and a selector absent from the shared stylesheet.

For every newly approved family or component, add a clear `description` and a real HTML `specimen` under `docs/ui/specimens/` to its catalog entry. The specimen must use the shared classes and actual shared CSS/JS; never paste CSS values into it. Compare computed styles for normal, hover, focus, active, open, selected and disabled states that apply to the component. Check the specimen against the existing production role, including native and enhanced select variants and single versus grouped checkboxes. Add assertions for the exact approved colors, borders, focus rings and dimensions; merely loading the shared stylesheet does not establish parity. Run `python tools/ui_standard.py render`, then `check` and `tests/ui_standard_gallery_browser_test.mjs` through the local browser wrapper. CI rejects a missing or stale gallery. The catalog `docs/ui/approved-components.json` is the machine-readable index; `docs/ui/approved-components.html` is its generated visual view. The canonical CSS and family `canon` file own exact values. Update impacted Notion memory only after the normal merge, following `AGENTS.md`.
